fix(protocol): flag refusals with the MCP error bit

Reported by #34: every refusal arrived with isError=false —
session_not_found, session_capacity_exceeded, session_recovering,
handle_not_found, invalid_operation_field, operation_text_too_large. PTK's
tools return a string, which the SDK always wraps as a successful call, so a
client trusting the protocol flag read "Nothing was executed" as success.
The real outcome was legible only by parsing bracketed in-band text, which
no MCP client does by default.

SupervisorCallFilter already wraps every tool call and already sets the flag
on its own refusals, so it is the seam: it now recognizes PTK's own leading
refusal markers ("[ptk <tool>] refused ...", "[ptk output] invalid request
...", "[operation not started]") and sets IsError on those responses. The
text is untouched, so anything parsing it is unaffected.

Deliberately NOT flagged: a script that ran and threw, a non-zero exit, an
empty result. Those are outcomes of work that happened; the call succeeded.
Only "nothing was executed" is an error at the protocol level. A user's own
output that happens to quote a refusal marker mid-line is not matched — only
a leading marker counts.

Verified against raw JSON-RPC from a live server: a refusal returns
"isError":true, ordinary work returns no isError at all. 16 table-driven
cases cover both directions, including the quoted-marker case.
