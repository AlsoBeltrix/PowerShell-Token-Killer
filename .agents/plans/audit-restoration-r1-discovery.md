## 2. Re-seating design

- Old wiring: `Program.cs` built `AuditStartupConfiguration` →
  registered `AuditRuntimeGate` as `IHostedService` → installed the
  audit call filter via `filters.AddCallToolFilter(...)`.
- Current head has exactly one call filter:
  `server/PtkMcpServer/Program.cs:58`
  (`filters.AddCallToolFilter(SupervisorCallFilter.Create())`) — the
  o53-3 disposition filter. **Re-seat: the audit admission filter
  composes ahead of the supervisor filter at this same anchor** —
  journal the admission before dispatch, observe completion after, and
  map an audit refusal to the structured `isError` verdict path the
  o53-3 contract already defines (a refusal is `NotStarted`,
  `safe_to_resubmit=true`).
- Topology note: sessions now execute in contained worker processes;
  the journal, spool, and exporter all stay supervisor-side (they were
  supervisor-side before — workers need no audit code).
- Quarantine-and-continue (rule 3) replaces the old terminal startup
  refusal: a failed artifact validation moves the artifact to a
  quarantine directory under the audit root, journals a quarantine
  event, and startup proceeds on clean storage. Only local write
  inability blocks.

## 3. Encoding decision (settled with evidence)

**Vendor the generated protobuf C# and drop `Grpc.Tools` from both
projects.** Evidence: the recorded ARM64 Linux blocker is a
protoc/MSBuild crash at build time; both `PtkMcpServer` (old) and
`PtkSiemReceiver` (current) carry `Grpc.Tools 2.82.0` + the same
`audit_otlp.proto`. Committing the generated `.cs` (regenerated by a
checked-in script on proto change, with a CI drift check comparing
fresh generation on an x64 leg) removes protoc from every build on
every platform while keeping: binary OTLP wire compatibility with
generic collectors, the receiver's existing parser untouched, and the
S4 byte-golden fixture methodology intact. The JSON-OTLP alternative
was considered and declined: it forces a new receiver ingest parser
and abandons byte-golden fixtures, a larger blast radius for the same
ARM64 result. Splunk/Sentinel adapters are plain JSON HTTP and never
touch protobuf.

## 5. Destination-adapter contract (design)

- One supervisor-side export pipeline: journal drain → bounded batch →
  `IAuditDestination.DeliverAsync(batch)` → acknowledged cursor
  advance. At-least-once; duplicates are the destination's problem
  (the receiver is already idempotent — S3).
- Adapter = endpoint + credential + format. Initial set: **PTK
  receiver** (OTLP protobuf + bearer token), **generic OTLP collector**
  (OTLP protobuf + bearer token), **Splunk HEC** (JSON events + HEC
  token), **Sentinel Logs Ingestion** (JSON + Entra client credential,
  DCR endpoint).
- Credentials live in the protected config store (0600/`SecureAuditStorage`
  conventions), never in the journal or logs; the settings page writes
  the exporter config atomically.

## 6. Receiver token-auth mode (design)

`siem/PtkSiemReceiver/Ingest/ReceiverApplication.cs` owns the Kestrel
ingest endpoint (client-cert mode today). Add an auth-mode
configuration: `token` (default — TLS server cert + `Authorization:
Bearer`, constant-time compare against a hashed-at-rest token issued at
setup and rotatable from the dashboard) | `mtls` (the existing S2
surface, unchanged, for hardened deployments). No pairing machinery
(owner ruling). The S3H protected-path boundary extends to the token
file before first use.
