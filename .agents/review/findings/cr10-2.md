# cr10-2: custody verification and retention are quadratic

**Severity**: HIGH — large receiver stores can take minutes or hours to start
and retention can stall while neither behavior is bounded independently.
**Status**: Reopened after final allowed review round; repair pending
**Branch**: —
**Commit**: `f739b244d6ff85444fae27a9032abad15397f231`

## Evidence

`siem/PtkSiemReceiver/Storage/SqliteIngestStore.Custody.cs` performs one
subject query for every custody receipt and uses `CAST(event_id AS TEXT)`,
which defeats the event primary-key index. Retention likewise deletes each
selected subject individually with the same cast instead of using one
set-based indexed operation.

## Predicted observable failure

Startup work grows quadratically with retained events and keeps both listeners
unbound; each size-retention batch repeats hundreds of scans. Claude measured
1,000 events at 41 ms and 8,000 at 1.7 s, matching the query plan's full scan.

## What

Per-receipt and per-deleted-row SQL turned a linear integrity pass and
set-based retention sweep into repeated full-table scans.

## Approach

Replace per-receipt live-source lookups with preloaded indexed subject maps,
and replace per-ID deletes with one typed temporary selection table or bounded
parameterized set operation. Pin query plans and near-linear work structurally
or with deterministic statement counts, not a timing-only test.

## Known gaps

age-only sweep selecting more than 32,766 rows fails before deletion and
retries the same permanently failing set forever. The follow-up repair must
use bounded typed batches (or a typed temporary selection table) without
restoring per-subject statements. This section has reached its two-round
review cap; the repair receives local guard proof but no third review round.
