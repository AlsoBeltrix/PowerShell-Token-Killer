# cr11-1: routed ingest path variants bypass the custody pause

**Severity**: HIGH — an accepted route variant can commit to a divergent
restore branch while custody is unhealthy or restore-pending.
**Status**: In progress
**Branch**: —
**Commit**: `cc8327555c9112a57405414af19c5a31cc88f316`

## Evidence

`siem/PtkSiemReceiver/Ingest/ReceiverApplication.cs` applied the custody gate
in pre-routing middleware only when `Request.Path == "/v1/logs"`, while
ASP.NET Core routes `POST /v1/logs/` to the same ingest handler.

## Predicted observable failure

During older-backup restore-pending state, `POST /v1/logs/` returns 200 and
commits an event and custody receipt. That advances the restored head and can
make the authenticated reconciliation endpoint reject the pending restore.

## What

The fail-closed mutation gate was attached to one raw path spelling rather
than to the routed operation that performs the mutation.

## Approach

Move the custody check into `HandleIngestAsync`, after admission succeeds and
before any request authentication or body buffering. Every path spelling that
routes to the handler is then gated by construction, while the existing
refusal-before-buffering and saturated-admission ordering remains intact.

## Guard proof

`CustodyWitnessTests::Older_backup_restore_requires_operator_authorization_and_alerts_once`
now asserts both `/v1/logs` and `/v1/logs/` return 503 while restore is
pending. Before the handler-bound repair, the added assertion failed with
actual status 200; after the repair it passes. `ReceiverAdmissionRefusalTests`
also passes, proving a saturated gate still refuses before consulting the new
dependency.
