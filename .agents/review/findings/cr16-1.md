# cr16-1: detached Apple submissions false-fail while still in progress

**Severity**: MEDIUM — a transient `notarytool` transport failure can make a
healthy Apple submission fail the release even though its durable status is
still `In Progress` and later becomes `Accepted`.
**Status**: Verified by independent guards; final Claude round unavailable
**Branch**: —
**Commit**: `b8cf442be8b1d9ae3fbd8520f152026626966f73`

## Evidence

The macOS release step submitted with `--wait --timeout 30m`. When that poll
stream did not contain `status: Accepted`, it extracted the submission id and
called `notarytool info` exactly once. Every result other than `Accepted`,
including the documented nonterminal `In Progress`, fetched the log and exited
1. Apple's installed CLI exposes `notarytool wait <submission-id>` specifically
to resume an existing submission and documents that the service keeps
processing after the client times out.

The same transport failure class occurred during the v0.2.2 release after
Apple had accepted the submission. The one-shot `info` recovery covered that
terminal timing but not the equally valid earlier timing where processing has
not finished.

## Predicted observable failure

If the initial wait loses its connection and the immediate status read returns
`In Progress`, the release job reports `notarization was not accepted` and
fails. Apple continues processing the already-uploaded payload; a later status
can be `Accepted`, so retrying the whole workflow needlessly creates another
submission and rebuild.

## Guard proof

`scripts/notarize-macos.sh` now captures and validates the canonical UUID from
a no-wait submission, then uses the dedicated `notarytool wait` command by id
for the remaining portion of one 30-minute allowance. A dropped wait is
followed by authoritative `info`; `In Progress` resumes the same submission,
only `Accepted` succeeds, terminal rejection fails with its log, and an
unknown status or missing/malformed id fails closed.

`scripts/test-notarize-macos.sh` replaces `xcrun` with a local fake and never
contacts Apple. Its load-bearing case returns a transport error from the first
wait, `In Progress` from `info`, and `Accepted` from the second wait, asserting
two waits and one status recovery. Separate cases guard terminal `Invalid`, a
missing id, and a malformed id. The local test passes. Replacing only the
`In Progress` recovery arm with the former immediate failure makes the test
fail at the expected `recover: expected exit 0, got 1`; restoring the arm makes
it pass again. Bash syntax, ShellCheck, `actionlint`, and `git diff --check`
pass.
