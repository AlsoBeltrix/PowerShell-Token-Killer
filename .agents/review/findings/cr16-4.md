# cr16-4: public signing claims include unsigned Linux assets

**Severity**: LOW — Linux users are told release binaries are signed even
though Linux assets carry checksum integrity but no publisher code signature.
**Status**: Repaired; final verification pending
**Branch**: —
**Commit**: pending final verification record

## Evidence

The public-install introduction described every supported asset as a signed
binary, and the Signing section opened with `Release binaries are signed`.
The release workflow Authenticode-signs Windows executables and Developer
ID-signs/notarizes macOS executables, but its Linux matrix legs perform no
publisher signing. All assets are covered by the release `SHA256SUMS` and the
installer verifies that checksum before extraction.

## Predicted observable failure

A Linux user can reasonably interpret the public contract as promising a
publisher-verifiable code signature, then find no signature or public key to
validate. The available checksum detects transfer corruption or mismatch
against the GitHub release manifest but is not the claimed platform publisher
signature.

## Guard proof

The public-install and Signing text now qualify signatures by platform. It
keeps the exact Windows Authenticode and macOS Developer ID/notarization
contracts, explicitly says Linux assets are not publisher code-signed, and
binds Linux integrity to `SHA256SUMS`. `-FromRelease` now distinguishes
preserving Windows/macOS signatures from checksum-verifying every platform.

`server/test-release-signing-docs.ps1` asserts all three platform contracts
and rejects the three former unqualified claims. It runs in ordinary CI on all
three operating systems. Restoring only the former public-install claim makes
the guard fail with `Public install still calls every platform binary signed.`;
restoring the qualified text makes it pass. PSScriptAnalyzer, `actionlint`, and
`git diff --check` pass.
