# cr2-1: Windows silently trusts an unprotected host identity instead of quarantining it

Severity: HIGH. Source: codereview codex (gpt-5.6-sol @ high, standard)
over `61fc838..a10ad50`, 2026-08-10. Status: CLOSED (accepted).

## Evidence

`server/PtkMcpServer/Audit/AuditJournalFactory.cs` `ReadHostId` called
`SecureAuditStorage.VerifyProtectedFile`, whose Windows leg REPAIRS the
file's owner/DACL instead of validating it — so a syntactically valid
foreign or over-permissive `host.id` never reached the quarantine catch.
Unix validated (mode check throws), making the platforms asymmetric on a
security property.

## Predicted observable failure

On Windows, pre-seeding `host.id` with a valid v4 GUID and an
over-permissive ACL causes startup to adopt that attacker-controlled
identity: no quarantine artifact, no diagnostic, and subsequent audit
events carry the spoofed host ID.

## What

Both `ReadHostId` verifications now use the non-mutating
`VerifyExternalProtectedFile` boundary: retained identities are validated
on every platform, a mismatch routes to quarantine-and-continue, and
protection application is reserved for files this process creates.

## Guard proof

  — source pin: the factory contains no repairing `VerifyProtectedFile(`
