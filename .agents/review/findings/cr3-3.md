# cr3-3: Retention monopolizes the receiver writer during repeated VACUUM

Severity: HIGH. Source: codereview codex (gpt-5.6-sol @ high, standard)
over `1a7a71f..98a3625`, 2026-08-10. Status: fixed; guard replaced and proved. Verification round 2 could not
see the bite because the dispatch pinned the wrong base (orchestrator
error, corrected below).

## Evidence

`SqliteIngestStore.EnforceRetentionAsync` took the same `_writerGate`
that `CommitAsync` uses and held it across the whole size loop, running
a full `VACUUM` after every 512-row batch; `RetentionService` runs its
first sweep before its first delay.

## Predicted observable failure

On a large database, live ingest commits and receiver readiness stall
for the duration of many full-database VACUUM passes — client timeouts
or admission-capacity refusals.

## What

Each pruning chunk now takes and releases the writer gate, so ingest
interleaves with retention, and compaction runs once after pruning
rather than per batch.

## Guard proof

Replaced. A timing test cannot prove this property (a small sweep is
instant, so it passed against the defect too), so the property is pinned
structurally:
`Retention_releases_the_writer_gate_between_pruning_chunks` requires the
pruning loop to both acquire AND release the writer gate inside the loop
and forbids per-batch compaction — proved to FAIL against the base file
and pass at head. `Ingest_completes_while_a_retention_sweep_runs` is
retained as its behavioral companion (it does not bite alone, and is
labelled as such).

## Reopen (verification round 1, 2026-08-10)

Verification returned `reopened` — not against the fix, which it judged
sound, but against the guard: it passed at BOTH base and head, so it
never proved anything. Recorded because a guard that does not bite is
indistinguishable from an untested fix.
