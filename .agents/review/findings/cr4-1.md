# cr4-1: A canonical non-v4 lineage id bypasses quarantine and disables execution

**Severity**: HIGH — one malformed ADVISORY artifact causes a complete

## Evidence

`AuditBootLineage.ReadPrevious` (AuditBootLineage.cs:55-63) accepts any
canonical GUID from `boot-lineage.json`, but the record serializer
requires `producer.previous_supervisor_boot_id` to be UUIDv4
(`AuditEvent.cs` `RequireNullableUuid(..., 4, ...)`). A protected
lineage file carrying a canonical UUIDv1 reaches the journal instead of
quarantine.

## Predicted observable failure

The `server.started` append fails schema validation
(`AuditEventValidationException` → lifecycle `FailLocked("journal.schema")`),
leaving the audit runtime unavailable and refusing every PTK execution
until the artifact is manually repaired.

## What

The lineage read validated canonical-GUID shape but not the v4
version/variant the schema demands, so a value the serializer would
reject flowed into every record instead of being quarantined.

## Approach

`ReadPrevious` now enforces the same v4 constraint the serializer does
(version nibble 4, RFC-4122 variant); any other value is corruption and
takes the existing quarantine-and-continue path (artifact preserved,
fresh state, fact journaled via the pending-startup-quarantine channel).

## Files changed

- `server/PtkMcpServer/Audit/AuditBootLineage.cs` — v4 validation in ReadPrevious

## Guard proof

`AuditBootLineageTests.A_canonical_but_non_v4_lineage_id_is_quarantined_not_served`
— writes a protected lineage file with a canonical UUIDv1; the journal
must open with a null predecessor, quarantine the artifact, park the
detail code, and a subsequent append must succeed. Reverting the fix
makes this FAIL (the journal opens with the v1 predecessor and the
append throws); restoring makes it PASS.
