# cr4-2: Lineage publication failures are silent, leaving a whole boot unattested

**Severity**: MEDIUM — requires a second loss event to become silent
loss, but the resulting full-boot loss is exactly the class boot lineage
exists to make visible.
**Status**: Verified
**Branch**: —
**Commit**: `54dd79f`

Reviewer: codex / gpt-5.6-sol / high / standard (generation pass over
`abc3292..8ab189a`, 2026-08-11).

## Evidence

`AuditBootLineage.TryPublish` (AuditBootLineage.cs:97-105) reduces
create/flush/rename failures to `false`; `AuditJournal.Append`
(AuditJournal.cs:578) merely retries on later appends. No health
condition or audit fact reports the failure.

## Predicted observable failure

When the audit root denies root-directory creates/renames while the
already-open spool segment stays writable (the cr3-2 round-10 squat
shape), calls continue and audit health stays "healthy" although the
boot is never attested. If this boot's segments later vanish
undelivered, its successor truthfully claims the last PUBLISHED
predecessor and the exporter reports no boundary — silent full-boot
loss.

## What

An attestation mechanism whose own failure is invisible degrades to the
pre-lineage world without anyone knowing.

## Approach

The journal counts consecutive failed publish attempts and surfaces the
condition in `AuditHealth` (visible on the `ptk_state` audit line as
`LINEAGE_UNPUBLISHED`), clearing it on the first successful publish.
Publishing stays non-gating: the append that carries the audit record
never fails because its attestation note could not be written.

## Guard proof

`AuditBootLineageTests.A_failed_lineage_publish_is_visible_and_heals` —
squats a directory on the lineage file name so publish fails, appends,
asserts the health snapshot reports the condition; removes the squat,
appends again, asserts the condition clears and lineage is published.
Reverting the fix makes the visibility assertion FAIL; restoring makes
it PASS.
