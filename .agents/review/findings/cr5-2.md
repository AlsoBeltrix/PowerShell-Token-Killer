## Evidence
`server/PtkMcpServer/Audit/Web/AuditAlertWebhookService.cs:58` — the
constructor unconditionally calls `CountQuarantine()`, whose line 227
materializes every quarantine filename with `Directory.GetFiles`;
`Program.cs:84` registers this hosted service, so construction happens
during host build, before PTK can accept calls — webhook configured or
not.

## Predicted observable failure
A large or slow quarantine directory blocks hosted-service construction
before PTK accepts calls; a sufficiently large directory can raise
`OutOfMemoryException` (the full filename array) and abort startup.

## What
Synchronous, unbounded filesystem work in a hosted-service constructor,
performed even when `webhook is null`. The only reason it exists is the
alert baseline ("alerts fire on NEW artifacts, not on history every
boot").

## Approach
The startup baseline count is removed entirely, not moved: every
quarantine writer (`AuditJournalFactory.QuarantineHostIdentity`,
`AuditBootLineage`, `AuditExportGapStore`) embeds the quarantine instant
in the filename (`name.yyyyMMddTHHmmssfffZ.guid`), so "new artifact" is
judged per file against the construction instant (`_startedUtc`) — the
constructor does no filesystem work at all. File times cannot answer
this (quarantine is a `File.Move`; the artifact keeps its original
times), which is why the filename instant is the only honest source.
`Directory.GetFiles` became lazy `EnumerateFiles` (no array to OOM). A
name with no parseable instant counts as new — an alerting channel
fails noisy, and acknowledgment silences it after one post. A
quarantine minted during startup (after construction, the historic
host-identity incident class) still alerts, which the moved-baseline
alternatives would have lost.
