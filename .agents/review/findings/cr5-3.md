# cr5-3: The records API silently reports partial evidence as a complete successful response

## Evidence
`server/PtkMcpServer/Audit/Web/AuditWebUiService.cs:360` — every
non-fatal segment-read exception is swallowed with a comment assuming it
is merely the locked live segment; lines 406 and 409 also suppress
live-reader and directory-enumeration failures before line 411 returns
an ordinary record list.

## Predicted observable failure
A closed segment unreadable through corruption, permissions, or an I/O
fault yields HTTP 200 from `/api/records` with that evidence omitted and
no partial/error marker.

## What
The read loop cannot distinguish "this is the live segment another
supervisor holds locked" (expected, served separately when ours) from
"a closed segment failed to read" (evidence loss that must be
reported). All failure classes collapse into silence.

## Approach
`ReadRecentRecords` classifies each closed-segment read failure instead
of swallowing all of them: a vanished file (`FileNotFoundException` /
`DirectoryNotFoundException`) is retention and stays silent; a
lock-shaped `IOException` on the newest segment of its boot — the one
position a live segment can occupy, the same structural rule
`FileAuditJournalSink` applies (`IsLockedSegment` + "nonterminal locked
is an anomaly") — is the expected live case; everything else is counted
and reported (bounded at 8 named segments). Live-tail and enumeration
failures are likewise carried (`live_tail_error`, `read_error`).
`/api/records` still returns 200 with every readable record, plus
`partial`, `unreadable_count`, `unreadable_segments`; the page shows a
warning banner when `partial` is true.

## Known gaps
A corruption-class `IOException` on the newest segment of a dead boot is
indistinguishable from a live lock by openability alone and passes as
expected-live; after any rotation or on any older segment it is
reported. This mirrors the exporter's own classification limit.
