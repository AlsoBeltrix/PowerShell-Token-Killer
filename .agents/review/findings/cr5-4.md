# cr5-4: A populated closed spool prevents the UI from reading the newest live records

**Severity**: MEDIUM — the journal is intact, but the incident-facing UI silently presents stale evidence as the newest.

## Evidence
`server/PtkMcpServer/Audit/Web/AuditWebUiService.cs:374` — the live-tail
read runs only while the accumulated list, already filled from closed
segments, holds fewer than `tail * 4` records.

## Predicted observable failure
With at least 4×tail records in closed segments, newer records in this
supervisor's live segment are never inspected; `/api/records` returns an
older closed-segment tail while claiming to be the newest records.

## What
The `lines.Count < tail * 4` loop condition was meant as a read bound but
doubles as a short-circuit: a busy root's closed spool satisfies it
before the live tail — which holds the *newest* records — is ever read.

## Approach
The live tail is read unconditionally: the `lines.Count < tail * 4`
loop condition became `while (true)`. The read stays bounded by the
live segment itself — rotation caps its size, and every pass either
advances the file-byte offset past a newline or breaks (no-data,
empty, or newline-less chunk) — so the closed-spool count no longer
plays any bounding role.
