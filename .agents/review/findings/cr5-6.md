## Evidence
`server/PtkMcpServer/Audit/Web/AuditAlertWebhookService.cs:194-205` —
failed delivery returns without retaining the emitted condition set; the
next pass rebuilds conditions only from current snapshots, and lines
171-174 discard the pass (and advance `_notifiedUnhealthy`) when the
condition has cleared.

## Predicted observable failure
An `audit_unhealthy` or `lineage_unpublished` alert receives a 5xx; the
condition recovers before the next 30-second pass; no retry is ever
sent. The commit message's own contract ("an undeliverable webhook keeps
the edge pending") is violated for any level-typed condition that heals.

## What
Pending-edge state is implicit: it exists only as the difference between
current snapshots and acknowledged values. Monotonic counters re-derive
the edge on the next pass, but level-typed conditions (unhealthy,
lineage) lose it the moment the level drops.

## Approach
Pending-edge state became explicit: observed edges join a `_pending`
map keyed by condition name (bounded by the seven-condition
vocabulary), fresher detail for an already-pending condition replaces
it, and only a successful post clears the map. A pass with no current
conditions still delivers whatever is pending, so a condition healing
before the retry no longer erases the observed edge. Acknowledged
baselines still advance only on success, as before.

posture (the journal, not the webhook, is the durable record).
