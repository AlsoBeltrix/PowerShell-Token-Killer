# cr7-3: The chains endpoint and dashboard poll are unbounded

**Severity**: HIGH — an ever-growing chains response plus overlapping ten-second dashboard refreshes can exhaust the shared receiver process and visibly slow ingest.

## Evidence
`siem/PtkSiemReceiver/Web/OperatorEndpoints.cs:269` — `/api/chains`
materializes every chain with an events count and no LIMIT; line 438's
`setInterval` starts a new refresh whether or not the last completed.

## Predicted observable failure
Growth in retained boots makes each poll scan more and allocate more;
past ten seconds per scan, refreshes overlap and pile up.

## What
The one endpoint without a bound, polled on a fixed interval.

## Approach
`/api/chains` is bounded like the other lists (newest boots first,
LIMIT 200, the response says whether it was truncated), and the
dashboard chains its refresh with a completion-scheduled `setTimeout`
instead of `setInterval`, so a slow scan can never overlap itself.

## Guard proof
- `The_chains_list_is_bounded_and_newest_first`: bound+1 boots → the
  response holds exactly the bound, leads with the newest boot,
  `truncated:true`. Revert removes the const the test references, so
  the proof used a faithful sabotage (limit `int.MaxValue`, `truncated`
  hardwired false — the pre-fix unbounded shape): FAILS sabotaged
  (`Assert.True(truncated)`), PASSES fixed. Note: event IDs in the
  corpus must be UUIDv7 — the first proof run 400'd at ingest on v4
  IDs and was redone after correcting them.
