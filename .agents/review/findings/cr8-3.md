# cr8-3: Alert and gap custody commitments omit the mutable evidence fields

**Severity**: HIGH — a store-writing attacker can rewrite alerts.detail, subject, config hashes, or a gap's head/resume fields without breaking any custody receipt: the ledger keeps verifying over forged evidence.
**Status**: Verified
**Branch**: master
**Commit**: `6648223`

Reviewer (generation): codex / gpt-5.6-sol / high / standard over
`b093dea..782d345` (R5c), verdict `findings` (7), capability_ok true,
2026-08-11.

## Evidence
`SqliteIngestStore.cs` — `AlertCustodyBytes` commits only
id/rule/item/transition; `GapCustodyBytes` only id/boot/claimed.
Neither covers detail, subject, config hashes, observed head,
disposition fields, or resume boundary.

## Predicted observable failure
UPDATE alerts SET detail=... leaves every receipt hash valid.

## What
The custody bytes were identity stubs, not evidence commitments.

## Approach
Versioned JSON snapshots as the committed bytes: alert receipts carry
every immutable creation field (rule, item, subject, created,
both config hashes, detail) and transitions carry prior→new state +
actor + utc; gap receipts carry boot, observed head, claimed,
opened, and per-transition disposition/actor/resume fields.
`System.Text.Json` does the framing (no delimiter injection).

## Files changed
- `siem/PtkSiemReceiver/Storage/SqliteIngestStore.cs` — snapshots.
- `siem/PtkSiemReceiver.Tests/` — tamper guard.

## Guard proof
- Recompute the creation receipt from the stored alert row (new
  framing); mutate `detail` in SQLite; recomputation must MISMATCH
  the stored receipt hash. FAILS pre-fix (bytes never covered
  detail — mutation invisible), PASSES fixed.
