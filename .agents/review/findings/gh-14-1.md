# gh-14-1: Log classification can hand structured JSON to lossy RTK shaping

**Severity**: HIGH — mixed command output can present a credible but false or
missing structured result to an orchestrating agent.
**Status**: In progress
**Branch**: `fix/issue-14-json-log-shaping`
**Commit**: `a3a89f8`
**Source**: GitHub issue #14

## Evidence

Issue #14 reports a command that emitted log/progress text followed by one
single-line JSON object. The inline rendering cross-spliced fields between
array elements even though the captured file was valid. `Compress-PtcOutput`
classifies a whole textual stream from the first forty non-empty lines; when
most are log-like, it sends every line, including the JSON record, through
`rtk log`.

A local RTK 0.43.0 probe with eight timestamped INFO lines followed by a JSON
object returned only the log summary, proving the delegated leg does not
preserve the structured record boundary.

## Predicted observable failure

Log-like prefixes cause the complete mixed stream to enter lossy log shaping,
which can drop or recombine a trailing JSON document before PTK applies its
own visibly labeled line/character bounds.

## Approach

Treat a self-contained line beginning and ending with JSON object or array
delimiters as a conservative structured-record boundary. Such mixed output is
not log-shaped; it stays on `Limit-PtcPassthrough`, whose elision is explicit
and never delegates structural rewriting to RTK. Pure log behavior remains
unchanged.

## Files changed

- `src/PwshTokenCompressor.psm1:457-474` — bypass whole-stream log shaping

- `tests/PwshTokenCompressor.Tests.ps1:1354-1365` — prove a log prefix plus
  two-element JSON object remains exact and never receives a PTK log label.
