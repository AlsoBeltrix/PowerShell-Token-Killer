# gh-15-1: Long-running child lifetime boundary is easy to misread

**Severity**: MEDIUM — treating an in-worker process as detached can lose paid work when an executing call times out and containment recycles the worker.
**Status**: Accepted; pending integration
**Branch**: `docs/issue-15-long-work-lifetime`
**Commit**: `aa0493d`
**Source**: GitHub issue #15

## Evidence

Issue #15 reports a long-running external reviewer launched by `ptk_invoke` that exceeded its foreground budget and died with the recycled worker after roughly ten minutes of paid work. The existing README said stateless work should use ordinary harness process facilities, but did not state that `Start-Process` inside PTK remains a contained worker descendant and is not a detach contract.

## Predicted observable failure

A caller launches a long process through `Start-Process` inside `ptk_invoke`, assumes the returned process is independent, then loses the process and its paid work on timeout, reset, close, worker replacement, or shutdown.

## What

Make the worker-owned process lifetime explicit and direct long stateless work to process facilities outside PTK, while preserving the approved no-background-job and no-detach product boundary.

## Approach

Expand both user and server long-running-work guidance. State that all processes created by `ptk_invoke`, including `Start-Process`, remain in the selected worker's containment tree and name every lifecycle event that ends them. Give the supported split: outside-PTK harness processes for stateless work that must survive worker recycle, or a dedicated PTK session with a sufficient foreground timeout for work that requires warm state.
