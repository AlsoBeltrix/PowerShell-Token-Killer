# i13-1: caller-controlled standard error can forge the worker exit kind

**Severity**: HIGH — a caller can make PTK report its own text as PTK's
classification of why the worker died, which is worse than the "unknown" the
change set out to replace: a wrong cause is more expensive than no cause.
**Status**: Reopened once, then fixed properly (see "Reopen" below)
**Branch**: — (default-branch mode)
**Commit**: (filled in after commit)

## Evidence

- `server/PtkMcpServer/Worker/WorkerDiagnosticTail.cs:73` — `Text` retains the
  final printable-ASCII line of the worker's standard error regardless of who
  wrote it. The printable guard proves the bytes are printable, not that PTK
  authored them.
- `server/PtkMcpServer/Worker/SessionWorkerClient.cs:56` — `Kind` accepts any
  line beginning `ptk_worker_exit kind=`, and `InvocationFailureCode` maps it
  to `worker_exit_<kind>`.

The worker runs the caller's script in-process, so `[Console]::Error` is the
same stream the worker writes its own exit diagnostic to. Confirmed live on
this box against session `docs`:
`[Console]::Error.WriteLine('ptk_worker_exit kind=FORGED detail=forged')`
returned success — user code reaches the worker's own standard error.

## Predicted observable failure

A caller writes `ptk_worker_exit kind=runtime_failure detail=runtime_failure`
to standard error and then kills the worker (`[Environment]::Exit(1)`). The
tool reports `detail=worker_exit_runtime_failure` and quotes the forged line
as `worker_said=...`, attributing a cause PTK never observed. An agent reading
that response reasonably concludes the worker is defective when its own script
killed it.

## What

The change classifies a worker death from a stream the caller shares with the
worker. Retention is fine; trusting the retained text as PTK's own vocabulary
is not.

## Approach

Keep the tail as untrusted evidence and stop deriving `detail=` from it.
Classify from the exit code, which the caller cannot author, and report the
retained line as clearly-labelled untrusted text. Reported by codex during the
i13 generation pass; the reviewer's `better_approach` named both this and a
supervisor-owned channel, and the cheaper option is taken because the exit
code already separates the classes the caller cannot forge.

## Files changed

- `server/PtkMcpServer/Worker/SessionWorkerClient.cs` — `WorkerExitException.Kind`
  now derives from the exit code instead of parsing the retained text.
- `server/PtkMcpServer/Worker/WorkerProcessExit.cs` — the per-class exit codes
  became `internal` so both sides read one definition.
- `server/PtkMcpServer/Sessions/WorkerSupervisor.cs` — the retained line is
  reported as `worker_stderr_tail(untrusted)=` rather than `worker_said=`.

## Guard proof

- `SessionWorkerClientTests.A_forged_exit_line_cannot_dictate_the_reported_kind`
  — a genuine-looking `ptk_worker_exit kind=runtime_failure` line paired with
  exit code 1 must report `worker_exited_unexpectedly`, never
  `worker_exit_runtime_failure`. Proved by restoring text-based parsing:
  the test FAILS, and PASSES again with the exit-code classification.

## Coder dispute (if any)

None. The finding is correct and the premise was verified live rather than
accepted on argument.

## Known gaps

The exit code itself is trustworthy on Windows; on Unix it is currently the
broker's code, which is a separate finding (i13-2).

## Reopen (2026-08-05, verification pass)

The first fix at `178acea` **did not close the finding** — it moved the
forgery from the text to the exit code. The caller's script runs inside the
worker, so `[Environment]::Exit(84)` picks any reserved code and PTK would
still have reported `worker_exit_runtime_failure`. The comment I wrote
claiming the exit code "cannot be forged from inside the script" was simply
wrong, and contradicted evidence already gathered in the same session.

There is no forgery-proof cause available on this path, so the corrected fix
stops asserting one. `WorkerExitException.Kind` is deleted; every unrequested
death reports `worker_exited_unexpectedly` — the one thing PTK observed
rather than was handed. The exit code and the retained line still travel,
now behind
`evidence(untrusted, may originate from the executed command):`.

Second guard: `A_caller_cannot_make_ptk_assert_a_cause` is a Theory over
three perfect imitations (the worker's own diagnostic wording paired with its
reserved exit code) asserting no `worker_exit_` classification is ever
emitted while the evidence still reaches the caller.
