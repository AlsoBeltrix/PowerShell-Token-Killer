# i13-2: Unix reports the broker's exit code, never the worker's

**Severity**: MEDIUM — the exit code is presented as the worker's, so a
recurrence carries misleading evidence on two of the five shipped platforms.
**Status**: Open
**Branch**: — (default-branch mode)
**Commit**: (filled in after commit)

## Evidence

- `server/PtkMcpServer/Worker/UnixWorkerProcessLauncher.cs:198` — `ExitCode`
  returns `_brokerExit.Result`, the broker process's exit status.
- `server/PtkMcpServer/Native/ptk_worker_broker.c:790` — once the broker reaps
  the worker it returns a fixed `64` after containment. Neighbouring paths
  return `71` and `74`. None of them relay the worker's own status.

## Predicted observable failure

A worker that dies with `ptk_worker_exit kind=runtime_failure` and exit code
84 is reported on Linux and macOS as `worker exit_code=64`. A worker killed by
a signal reports 64 as well, instead of the `128+signal` the comment on that
property claims. Every Unix death reports the same constant, so the exit code
distinguishes nothing there.

## What

The commit's comment asserts the broker "relays the worker's status". It does
not — it reports its own containment outcome.

## Approach

Do not present the broker's status as the worker's exit code. Either relay the
real status from the broker, or report absent on Unix rather than a number
that is always 64. Absent is honest and costs nothing the platform can
currently provide; relaying properly is a broker protocol change and is
tracked as follow-up rather than smuggled into a review fix.

## Files changed

- `server/PtkMcpServer/Worker/UnixWorkerProcessLauncher.cs` — `ExitCode` is
  now unconditionally `null` on Unix, with the reason recorded at the property.

## Guard proof

- `SessionWorkerClientTests.Without_an_exit_code_the_diagnostic_still_reaches_the_caller`
  — with no exit code, no kind is claimed (`worker_transport_closed`) but the
  worker's retained line still reaches the caller. This is the shape Unix now
  produces; the assertion fails if a future change either invents a
  classification without a trustworthy code or drops the evidence.

## Consequence accepted

With i13-1, classification derives from the exit code, so Unix now produces no
`worker_exit_<kind>` at all — three of the five shipped RIDs. That is the
honest state: no trustworthy signal is available there today, and the retained
diagnostic still carries what the worker said. Relaying the real status
requires a new broker event (`ptk_worker_broker.c` discards the `waitpid`
status it already holds at line 416), which is a protocol change the #13 plan
excludes. Recorded as follow-up, not smuggled into a review fix.

## Coder dispute (if any)

None. Verified directly in the broker source.

## Known gaps

Relaying the true worker status through the broker remains desirable and is
not done here; this fix stops the misreport.
