# i13-3: an already-known worker death reports nothing on the next call

**Severity**: MEDIUM — the facts #13 exists to surface are discarded on a path
that is likely in practice: the call right after the worker dies.
**Status**: Open
**Branch**: — (default-branch mode)
**Commit**: (filled in after commit)

## Evidence

- `server/PtkMcpServer/Worker/SessionWorkerClient.cs:763` — `NextRequestId`
  throws a fresh `IOException("Worker transport is unavailable.")` when
  `_fatal` is already completed, discarding the `WorkerExitException` sitting
  in `_fatal`.
- `server/PtkMcpServer/Worker/SessionWorkerClient.cs:894` —
  `WithWorkerExitAsync` consults `_fatal` only when the caught exception is an
  `EndOfStreamException` or `ObjectDisposedException`, so the manufactured
  `IOException` never reaches the lookup.

## Predicted observable failure

The worker dies and `ObserveExitAsync` records the cause. A subsequent invoke
arriving before the session flips to recovering returns
`status=not_started detail=worker_transport_unavailable` with no exit code and
no diagnostic — even though both are already known and stored. The caller is
told less than PTK knows.

## What

The classification only reaches callers that raced the death. A caller that
arrives just after it gets the pre-#13 answer.

## Approach

Prefer an existing `WorkerExitException` from `_fatal` whenever one is
recorded, rather than gating the lookup on the incoming exception type.

## Files changed

- `server/PtkMcpServer/Worker/SessionWorkerClient.cs` — `WithWorkerExitAsync`
  now prefers a recorded `WorkerExitException` before inspecting the incoming
  exception's type; the lookup is extracted as `RecordedWorkerExit`.

## Guard proof

- `SessionWorkerClientTests.The_call_after_a_death_reports_the_recorded_cause`
  — kills the worker on a first call, then asserts the *second* call still
  reports `worker_exit_runtime_failure` and exit code 84. Proved by restoring
  the type gate: the test FAILS, and PASSES with the recorded-exit preference.

## Coder dispute (if any)

None.

## Known gaps

None. One correction found while fixing: preferring the recorded death
unconditionally was too broad — it replaced specific detail codes
(`truncated_frame`, `worker_transport_unavailable`) with the blanket
`worker_transport_closed`, caught by two pre-existing tests. The preference
now applies only when the recorded death carries a kind, an exit code, or a
diagnostic, and never over a `WorkerProtocolException`/`WorkerProcessException`
that already names something specific.
