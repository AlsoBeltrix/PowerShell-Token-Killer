# or5-3: an explicitly closed session is silently resurrected by host recovery

**Severity**: MEDIUM — recovery recreates a worker (process, runspace,
generation) for a session the operator explicitly closed, contradicting
the plan's "a closed alias is not speculatively opened".
**Status**: Open
**Branch**: `feature/mcp-resilience-r1` (worktree `.claude/worktrees/mcp-resilience-r1`)
**Commit**: —

## Evidence
`FrozenDefaultSessionState.AliasState.Binding` is immutable and always
declared `DesiredSessionState.Ready`; close only mutates observed state;
the recovery manifest is built from those bindings, and
`WorkerPrivateHostRuntime.ValidateInitialization` creates a slot for every
Ready binding.

## Predicted observable failure
`ptk_session close name=scratch` succeeds; the host later dies and
recovery launches a fresh worker for `scratch` because its binding still
says Ready — resurrecting a closed session.

## What
Move desired state out of the immutable binding into mutable per-alias
state (or rebuild the binding on each explicit lifecycle transition):
close sets desired=Cold, open/restart sets desired=Ready, so the recovery
manifest carries the operator's last explicit intent. The default alias
keeps frozen Ready by design.

## Guard proof
New test: close a dynamic alias, then a manifest built afterward declares
it Cold (host init creates no slot for it).

Empty.

coder had previously rationalized the behavior as matching the default
