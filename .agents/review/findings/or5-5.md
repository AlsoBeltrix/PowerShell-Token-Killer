# or5-5: recovery-machine integration order — land the thinnest live loss path first

**Severity**: MEDIUM — wiring the 2,602-line state machine as written
forces a per-alias lifecycle epoch through three just-landed components in
lockstep; meanwhile the shipped product has no worker-death detection at
all (operations keep dispatching at a dead worker).
**Status**: Open
**Branch**: `feature/mcp-resilience-r1` (worktree `.claude/worktrees/mcp-resilience-r1`)
**Commit**: —

## Evidence
`SessionRecoveryStateMachine` has zero production callers; its transitions
advance the alias transition version while both integration ends pin that
version at 1 and reject anything else (`FrozenDefaultSessionState`,
`WorkerPrivateHostRuntime.ValidateAndBind`). Nothing clears a dead
worker's slot today.

## Predicted observable failure
Wiring the machine as written reworks the sub-slice 3/4 spine against
2,727 lines of tests pinning the single-epoch behavior on the other side.
Until any wiring lands, an unexpected worker exit leaves operations
dispatched at a dead worker, surfacing repeated outcome_unknown.

## What
Invert the order: land the thinnest end-to-end
loss → confirm-death → next-generation → relaunch path per alias, wired to
the real slot/containment resources and integrated with the existing
transition-version contract (the machine's epoch stays its private
bookkeeping inside the host, never on the wire), then grow the machine's
states and backoff/half-open behavior behind that live seam. Manual and
automatic lifecycle transitions on one alias are single-flight arbitrated
in one place, so no epoch is needed on the wire. This matches the owner's
2026-07-24 direction.

## Guard proof
One-alias crash/recovery test while a second alias keeps its PID,
generation, warm state, and successful operation.
