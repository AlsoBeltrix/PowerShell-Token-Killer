# r6x-1: Windows evidence anchoring fails past MAX_PATH because `PublishAtomically` moves through a raw `MoveFileEx` P/Invoke

**Severity**: HIGH — on Windows, any script-evidence anchoring whose published
path exceeds 259 characters fails, degrading the private host to
`audit=unavailable` / `failure_class=evidence.storage`. Because audit is
fail-closed by design, that blocks ordinary invoke for the rest of the
session.

## Evidence

`server/PtkMcpGuardian/Audit/SecureAuditStorage.cs:210-218` publishes through a
raw Win32 P/Invoke:

```csharp
if (OperatingSystem.IsWindows())
{
    if (!WindowsNative.MoveFileEx(
            temporaryPath, publishedPath, WindowsNative.MoveFileFlags.WriteThrough))
    {
        throw new Win32Exception(Marshal.GetLastPInvokeError());
    }
}
```

`server/PtkMcpGuardian/Audit/ScriptEvidenceStore.cs:1280-1300` builds the

`server/PtkMcpGuardian/Audit/ScriptEvidenceStore.cs:378-386` calls
`RenameArtifact` → `PublishAtomically` for the `AwaitingAnchor → Anchoring`
transition; `:397-400` then swallows the cause

Measured on `NETWATCH-01` at head `5e8b3be` with a throwaway probe on the

```
err=3 (ERROR_PATH_NOT_FOUND)  srcLen=216  dstLen=317
dst=C:\Users\michael\.ptk-script-evidence-tests-85f897ab38dc4619bb228e72df77c7f3\
    anchor-recovery-audit\evidence\9c968d26-...-0ec4e8e41835.4e9e8bb9...f88dd.
```

The 216-character *source* was created successfully by BCL file APIs, which
normalize to `\\?\` automatically. The 317-character destination fails because
a hand-written P/Invoke gets no such normalization. `LongPathsEnabled=1` is
already set on this host and does not rescue it — that switch only helps
processes whose manifest declares `longPathAware`, which the test host does
not.

## What

`SecureAuditStorage`'s Windows publish path is a raw `MoveFileEx` P/Invoke, so
it inherits the legacy 260-character `MAX_PATH` limit that the rest of the
component escapes by going through the BCL. The evidence store's anchoring
filename is unusually long by construction (two GUIDs, a 64-char digest, a
32-char boot ID and a 20-digit sequence), so it crosses the limit under
ordinary user-profile roots without anything being misconfigured.

## Approach

Every raw Win32 path argument in the component gets extended-length form, at
the P/Invoke boundary only. A standalone Windows probe measured all four raw
path consumers before any product code was written, so the remedy is grounded
in observed behaviour rather than inference:

| raw consumer | plain path >259 | extended-length |
|---|---|---|
| `MoveFileEx` | `err=3` `ERROR_PATH_NOT_FOUND` | ok |
| `CreateFileW` | `err=3` `ERROR_PATH_NOT_FOUND` | ok |
| `FILE_RENAME_INFO` destination | `err=206` `ERROR_FILENAME_EXCED_RANGE` | ok |
| advapi32 name-based (`SetNamedSecurityInfo` family) | `123` `ERROR_INVALID_NAME` | ok |

All four were live-broken, so all four are converted. Two properties keep the
change from disturbing the security posture it sits inside:

1. **The prefix never escapes the P/Invoke boundary.** Managed paths stay
   unprefixed, because that is the form every check and comparison here
   speaks: `GetProtectedFileIdentity` compares against `NormalizeFinalPath`,
   which strips exactly this prefix off `GetFinalPathNameByHandle` output.
   `ReplaceFileAtomically` therefore still hands `GetProtectedFileIdentity`
   the unprefixed path, marked at the call site.
2. **`Path.GetFullPath` runs before the prefix goes on.** `\\?\` disables
   kernel path normalization, so resolving first is what keeps the component's
   link, reparse-point, and direct-child refusals meaningful instead of
   handing the kernel something unnormalized.

`MoveFileEx` sits behind a `MoveFileExtended` wrapper so no call site can
forget the boundary. The import keeps its original attribute shape and member
name deliberately: `PtkGuardianArchitecture.Tests` pins the guardian's
native-import closure exactly and is fail-closed, and a first cut that set
`EntryPoint = "MoveFileExW"` was correctly rejected by it as an unapproved
new import. Naming the wrapper apart from the import leaves that audited
closure untouched rather than re-pinning a security allowlist to fit this
change.

## Coder dispute

Not a dispute about the defect — it is real and measured. The dispute is about
authority to fix it here. This is `SecureAuditStorage`, the protected-path
security boundary hardened by mini-SIEM S3H and guarded by
`RefuseLinkedPathComponents` / `RequireDirectChild` /
`RefuseLinkOrReparsePoint`. `\\?\` paths deliberately bypass Win32 path
normalization, so introducing them next to those refusals changes the risk
profile of a security boundary — "changed risk" under `AGENTS.md`, which stops
even inside the owner-authorized R2-R7 sequence. Recorded for the owner rather
than repaired unilaterally.

## Known gaps

- **Adjacent, deliberately out of scope: the worker/launcher native path
  consumers are still unnormalized.** `WindowsWorkerNative.CreateFileW(string
  fileName, …)` and `WindowsWorkerNative.CreateProcessW(string
  applicationName, …)` take raw Windows paths with the same missing
  normalization. They are a different subsystem with a different path
  population (install/package layout and pipe names, not 209-character
  evidence leaves), so no failure is observed there and none is claimed. This
  fix is scoped to the audit/evidence storage component the owner authorised;
  the worker-side exposure is recorded in `.agents/state.md` under
  `## Open / Parked` rather than folded in silently. `BackgroundJobContainment`
  and `FileAuditJournalSink`'s kernel32 imports are NOT exposed — the former
  takes a job-object name, the latter is handle-based.
- `ShellDialectWiringTests.Route_pwsh_bypasses_detection_as_consent` also
  fails on Windows and is deliberately **not** attributed to this finding; it
  is undiagnosed.
- The reviewer runs on macOS, where both new guards no-op, so no reviewer can
  independently reproduce the red-to-green proof. The Windows run above is the
  only evidence for it, and the dispatch says so explicitly so a verdict
  cannot silently imply otherwise.
- The relationship to GitHub #9/#10 is a strong hypothesis, not proven. Those
  reports show a Windows fail-closed audit wedge with no in-band recovery,
  which is this failure's signature, but they recorded
  `failure_class=journal.startup` where this reproduces
  `failure_class=evidence.storage`. Both are the same fail-closed audit
  boundary reached by different paths; proving or refuting the link needs the
  reporting host's audit-root path length.
