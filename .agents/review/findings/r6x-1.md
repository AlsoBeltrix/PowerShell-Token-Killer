# r6x-1: Windows evidence anchoring fails past MAX_PATH because `PublishAtomically` moves through a raw `MoveFileEx` P/Invoke

**Severity**: HIGH — on Windows, any script-evidence anchoring whose published
path exceeds 259 characters fails, degrading the private host to
`audit=unavailable` / `failure_class=evidence.storage`. Because audit is
fail-closed by design, that blocks ordinary invoke for the rest of the
session, and it is the root cause of four `Windows_*` real-composition
acceptance tests plus three `ScriptEvidenceStoreTests`.
**Status**: Open
**Branch**: (none — no fix authored; owner ruling pending, see Coder dispute)
**Commit**: (none)

## Evidence

`server/PtkMcpGuardian/Audit/SecureAuditStorage.cs:210-218` publishes through a
raw Win32 P/Invoke:

```csharp
if (OperatingSystem.IsWindows())
{
    if (!WindowsNative.MoveFileEx(
            temporaryPath, publishedPath, WindowsNative.MoveFileFlags.WriteThrough))
    {
        throw new Win32Exception(Marshal.GetLastPInvokeError());
    }
}
```

`server/PtkMcpGuardian/Audit/ScriptEvidenceStore.cs:1280-1300` builds the
anchoring name, which is 209 characters before the root is prepended:

```
{evidenceId(36)}.{scriptDigest(64)}.anchoring.{SupervisorBootId:N(32)}.{Sequence:D20}.{EventId(36)}.script
```

`server/PtkMcpGuardian/Audit/ScriptEvidenceStore.cs:378-386` calls
`RenameArtifact` → `PublishAtomically` for the `AwaitingAnchor → Anchoring`
transition; `:397-400` then swallows the cause
(`catch (Exception exception) when (!IsFatal(exception)) { throw new
ScriptEvidenceStorageException(); }`), so the real error never reaches a log.

Measured on `NETWATCH-01` at head `5e8b3be` with a throwaway probe on the
`MoveFileEx` failure path:

```
err=3 (ERROR_PATH_NOT_FOUND)  srcLen=216  dstLen=317
dst=C:\Users\michael\.ptk-script-evidence-tests-85f897ab38dc4619bb228e72df77c7f3\
    anchor-recovery-audit\evidence\9c968d26-...-0ec4e8e41835.4e9e8bb9...f88dd.
    anchoring.1234567812344abc8def0123456789ab.00000000000000000001.
    019f97a7-b654-77b8-97fb-9db336be1e0f.script
```

The 216-character *source* was created successfully by BCL file APIs, which
normalize to `\\?\` automatically. The 317-character destination fails because
a hand-written P/Invoke gets no such normalization. `LongPathsEnabled=1` is
already set on this host and does not rescue it — that switch only helps
processes whose manifest declares `longPathAware`, which the test host does
not.

## Predicted observable failure

On Windows, with an audit root deep enough that the 209-character anchoring
name crosses 259 total characters:

1. `ScriptEvidenceStore.MarkAnchored` throws `ScriptEvidenceStorageException`.
2. The audit subsystem degrades to `failure_class=evidence.storage`, and
   `ptk_state` returns the degraded text block (`audit=unavailable`,
   `unrecorded=true`) instead of public-state JSON.
3. Fail-closed audit then blocks ordinary invoke for the session.

Caught today by, on `NETWATCH-01` and green on Linux ARM64 at the same head:

- `PtkMcpServer.Tests.ScriptEvidenceStoreTests.Restart_promotes_only_checkpoint_proved_anchoring_state`
- `PtkMcpServer.Tests.ScriptEvidenceStoreTests.Young_checkpointed_anchor_is_quota_eligible_without_age_expiry`
- `PtkMcpServer.Tests.ScriptEvidenceStoreTests.Anchor_lease_blocks_gc_until_checkpoint_then_enables_age_and_quota_retention`
- `PtkMcpGuardian.Tests.ProductionGuardianCompositionTests.Windows_composition_classifies_real_prewrite_loss`
- `PtkMcpGuardian.Tests.ProductionGuardianCompositionTests.Windows_composition_requires_explicit_repair_after_ambiguous_reset`
- `PtkMcpGuardian.Tests.ProductionGuardianCompositionTests.Windows_composition_never_replays_a_real_effect_when_the_host_dies`
- `PtkMcpGuardian.Tests.ProductionGuardianCompositionTests.Windows_composition_keeps_a_real_job_tombstone_and_sealed_output`

The first three are direct; the four composition tests are downstream — they
need a healthy replacement private host and get a degraded one.

## What

`SecureAuditStorage`'s Windows publish path is a raw `MoveFileEx` P/Invoke, so
it inherits the legacy 260-character `MAX_PATH` limit that the rest of the
component escapes by going through the BCL. The evidence store's anchoring
filename is unusually long by construction (two GUIDs, a 64-char digest, a
32-char boot ID and a 20-digit sequence), so it crosses the limit under
ordinary user-profile roots without anything being misconfigured.

## Approach

Not authored. The shape of a fix is to give every raw Win32 path argument in
this component extended-length (`\\?\`) form, or to route the publish through
a primitive that normalizes. Both interact with the component's security
posture, which is why this is an owner gate rather than an autonomous repair
(see Coder dispute).

## Files changed

None yet. A fix would touch at least:

- `server/PtkMcpGuardian/Audit/SecureAuditStorage.cs` — the publish primitive
  and, for consistency, every sibling Win32 path call
- possibly `server/PtkMcpGuardian/Audit/ScriptEvidenceStore.cs` — if the
  chosen remedy shortens the anchoring name instead

## Guard proof

Not yet produced. The natural guard is a Windows test that anchors evidence
under a root long enough to cross 259 characters and asserts the publish
succeeds; it must fail with the current `MoveFileEx` call and pass after the
fix. Today's three `ScriptEvidenceStoreTests` already fail on Windows, but
they are incidental witnesses (their root happens to be long), not a
deliberate guard on the boundary.

## Coder dispute

Not a dispute about the defect — it is real and measured. The dispute is about
authority to fix it here. This is `SecureAuditStorage`, the protected-path
security boundary hardened by mini-SIEM S3H and guarded by
`RefuseLinkedPathComponents` / `RequireDirectChild` /
`RefuseLinkOrReparsePoint`. `\\?\` paths deliberately bypass Win32 path
normalization, so introducing them next to those refusals changes the risk
profile of a security boundary — "changed risk" under `AGENTS.md`, which stops
even inside the owner-authorized R2-R7 sequence. Recorded for the owner rather
than repaired unilaterally.

## Known gaps

- The remedy choice is open: normalize the Win32 arguments, or shorten the
  anchoring name. Shortening changes on-disk evidence naming, which the
  inventory parser depends on (`ScriptEvidenceStore.cs:912` indexes a fixed
  101-character prefix), so it is not obviously the smaller change.
- `ShellDialectWiringTests.Route_pwsh_bypasses_detection_as_consent` also
  fails on Windows and is deliberately **not** attributed to this finding; it
  is undiagnosed.
- The relationship to GitHub #9/#10 is a strong hypothesis, not proven. Those
  reports show a Windows fail-closed audit wedge with no in-band recovery,
  which is this failure's signature, but they recorded
  `failure_class=journal.startup` where this reproduces
  `failure_class=evidence.storage`. Both are the same fail-closed audit
  boundary reached by different paths; proving or refuting the link needs the
  reporting host's audit-root path length.
