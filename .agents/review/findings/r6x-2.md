## What

These were originally lumped into `r6x-1` on the theory that one degraded audit
subsystem explained all four `Windows_*` composition failures. Fixing `r6x-1`

## Diagnosis of #1 (ambiguous reset) — root cause found 2026-07-25

**An ambiguous session outcome is silently erased by the replacement host's
declared-session restoration, permanently.** It is not a timing race in the
test.

Measured on `NETWATCH-01` at head `3ecc86f` with a throwaway probe that keeps
polling `ptk_state` after the point where the test asserts. Across 61 samples
spanning 6 seconds the session never changes:

```
t0  hostReady=True hostGen=2 sess=Ready warmLost=True boot=Restored
...
t60 hostReady=True          sess=Ready warmLost=True boot=Restored
```

`boot=Restored` is the tell: `BootstrapState.Restored` is only ever written by
the Ready branch of `FrozenDefaultSessionState.ObserveSessionLifecycle`
(`FrozenDefaultSessionState.cs:335-353`, committed at `:391-394`). So the
sequence is:

1. The ambiguous `ptk_reset` makes `GuardianHostSupervisor` call
   `ObserveSessionRecoveryUnknown` (`GuardianHostSupervisor.cs:2431` or
   `:3232`), which sets the alias to `RecoveryUnknown`, `ReadyForEffects=false`,
   `BootstrapState=Unknown` (`FrozenDefaultSessionState.cs:398-414`).
2. The lost host is replaced, and the replacement's declared-session
   restoration emits a **Ready** `SessionLifecycleEvent`.
3. `ObserveSessionLifecycle`'s Ready branch overwrites `State`,
   `ReadyForEffects` and `BootstrapState` unconditionally. Nothing consults
   whether the alias is sitting in an unrepaired `RecoveryUnknown`.
4. Nothing ever restores it, so the alias projects `Ready` and
   `ReadyForEffects=true` for the rest of the session.

Confirmed structurally: `RecoveryUnknown` appears in
`FrozenDefaultSessionState.cs` at exactly two lines — the method at `:398` and
its assignment at `:409`. There is no stickiness, no repair gate, and no
guard on the Ready path.

**Why this matters beyond a red test.** The snapshot type enforces
`readyForEffects == (state == Ready)`
(`PtkSharedContracts/Public/PublicState.cs:152`), so the alias does not merely
look wrong — it is projected as fully usable. R6's contract is that ambiguity
becomes `recovery_unknown` and that ordinary session work stays blocked until
an explicit lifecycle result repairs the alias
(`.agents/plans/mcp-resilience.md`, R6 sub-slice 5;
`GuardianHostSupervisorContracts.cs:206-212`). A model can therefore dispatch
work into a session whose reset outcome is unknown — the exact no-replay
boundary the design exists to protect.

**Inferred, not proven: macOS passes by ordering luck rather than by
protection.** The product has no guard on either platform; the plausible
reading is that on macOS the ambiguous marking happens to be committed after
the ready lifecycle and therefore survives, while on Windows the replacement
completes first and overwrites it. Confirming that needs the same probe run on
macOS, which has not been done. Either way the invariant is unenforced
everywhere, so this should not be treated as Windows-specific behaviour.

## Diagnosis of #3 (job tombstone / sealed output) — root cause found 2026-07-25

**Background-job output is never sealed by the production worker runtime, on
any platform.** One defect, not two, and not Windows-specific. The earlier
two-defect reading recorded here (3a "a Windows forwarding hop delivers zero
bytes", 3b "the test polls the wrong marker") is superseded; both errors and
what caused them are kept below under "Superseded readings" because the
mistakes are instructive.

### Root cause

`WorkerPrivateHostRuntime` never calls
`IPrivateHostOutputTransfer.CreateExecutionCapture`. Grep the production
runtime for output work and only two calls exist, both `TransferTextAsync`
(`WorkerPrivateHostRuntime.cs:550` foreground, `:685` the `job_output`
operation). The runtime it replaced does create one, for both invoke kinds:

```csharp
// DefaultPrivateHostRuntime.cs:213-229
if (request.Operation is
        InvokeForegroundOperation or InvokeBackgroundOperation)
{
    capture = _outputTransfer.CreateExecutionCapture(request) ?? ...
```

So under the worker runtime an `invoke_background` request registers a guardian
output capability that nothing ever writes to. The consequences chain exactly to
the observed symptom:

1. The job runs in the worker. The worker holds no capture (nothing in
   `PtkMcpServer/Worker/` references output capture at all), so its
   `job_terminal` reports `outputState=unavailable, outputBytes=0`
   (`WorkerPreparedOperationScheduler.cs:668-675`).
2. The guardian deliberately retains the unsealed background capability after a
   successful start — `GuardianOutputCoordinator.ResolveResponse` returns early
   for `InvokeBackground` and waits for a terminal that never comes
   (`GuardianOutputCoordinator.cs:164-174`).
3. `TryGetJobRecovery` therefore has no entry, so the job-status decoration at
   `GuardianHostSupervisor.cs:3181-3194` never fires and the worker's own
   `recovery=unavailable: output capture unavailable` text reaches the model
   unchanged.
4. At teardown the capability is finally terminalized by `AbandonGeneration`,
   which is the `PublishIncomplete reason=host_generation_lost bytesReceived=0`
   record the Windows instrumentation caught.

The regression window is the R6 production cutover `1e19b46`, which replaced
production selection of `DefaultPrivateHostRuntime` with
`WorkerPrivateHostRuntime`. That slice's own record claims it "forwards
foreground and job output" — true for both `TransferTextAsync` sites, but the
background capture was dropped.

### Reproduction on macOS

The saved probe is `r6x-2-3a-repro.patch` in this directory: a cross-platform
composition test that starts one background job
(`Write-Output 'PTK_R5_SEALED_JOB_OUTPUT'`) and polls `ptk_job status` 80 times
at 25 ms. On macOS at `dd29bc9` it never seals:

```
PROBE_STATUS[0]>>>job 1: running (pid 98522), ... recovery=unavailable: output capture unavailable
PROBE_STATUS[2]>>>job 1: exited 0, output completeness unknown, ... recovery=unavailable: output capture unavailable
PROBE_SEALED_AT>>>-1
```

The status settles within ~50 ms and never changes again, so this is not a
timing window. It is the identical signature the Windows test reports, which is
what establishes the defect is platform-neutral.

### Superseded readings, and why they were wrong

- **"A Windows forwarding hop delivers zero bytes."** The Windows evidence was
  correct and the inference was not: the test is Windows-gated, so a
  platform-neutral defect could only ever be *observed* on Windows. Nothing was
  run on another platform before concluding "Windows-specific". The same
  mistake pattern as #1, where "macOS passes by ordering luck" turned out to be
  the right call only because it was labelled an assumption.
- **"The test polls the wrong recovery marker."** Wrong; line 1857 is correct
  as written. There are two renderers and the test uses each correctly:
  - live job status is decorated by the guardian —
    `GuardianOutputResponseDecorator.Decorate` replaces the host's generic
    unavailable marker with `recovery=available: ptk_output handle=`
    (`GuardianOutputResponseDecorator.cs:29-40`), reached from
    `GuardianHostSupervisor.cs:3184-3193`. Line **1857** expects exactly this.
  - a job **tombstone** is rendered by `JobRecoveryStatus`, which emits
    `recovery=handle:` (`GuardianHostSupervisor.cs:1335`). Line **1902**
    expects exactly this.
  The cited counter-evidence did not say what it was read as saying:
  `JobManagerTests.cs:603-605` pins `SessionRuntime.RecoveryStatus`, the
  in-process legacy renderer, not the guardian composition path. **No test
  change is required for #3.** Had the "one-line test fix" been applied it would
  have broken a correct assertion.

### Fix (2026-07-25)

Implemented as described in the approach below.

- `WorkerPrivateHostRuntime.ExecuteBackgroundAsync` creates the execution
  capture, prepares it against the request deadline, and registers it in the new
  per-alias `JobCaptures` map inside the same lock that reserves the job
  capability — the terminal is what seals it, so it has to be findable before
  the job can produce one.
- `ReleaseJobTerminal` takes the capture and hands it to
  `SealBackgroundJobOutput`, which fetches the job's output over the worker
  request protocol and seals it. The fetch is fire-and-forget because the
  terminal callback holds both the bridge's and the runtime's lock.
- `ReleaseUnstartedBackgroundJob` disposes the capture when a job never starts
  (no terminal is coming), and `ClearAliasJobsLocked` disposes captures wherever
  an alias's job records are dropped — worker death, fault, reset, restart,
  shutdown. All five former `OutstandingJobs.Clear()`/`CompletedJobs.Clear()`
  pairs now route through that one helper.

**Deliberately not sealed rather than sealed empty.** A failed or unparseable
fetch leaves the capability unsealed, so the guardian reports the artifact
unavailable — true. Sealing an empty artifact would advertise a handle to
content the host never read.

**Known limit, recorded rather than hidden:** the seal takes a single
`job_output` read at offset 0, which the worker bounds at 128 KiB
(`JobManager.ReadOutput`'s `maxBytes` default). A job whose output exceeds that
seals only its first chunk while reporting complete. The pre-existing
`ptk_job output` transfer (`WorkerPrivateHostRuntime.cs`, `transferOutput:
true`) has the same shape, so this matches shipped behaviour rather than
introducing a new inconsistency — but it is worth its own follow-up.

### Guard proof (#3)

Two layers, both new:

- `ProductionGuardianCompositionTests.Composition_seals_a_real_background_job_artifact_for_handle_recovery`
  — the end-to-end proof on the real apphost, and **cross-platform by design**,
  closing the coverage gap this finding already identified for #1. It starts a
  real background job, polls `ptk_job status` until it advertises a sealed
  artifact, extracts the `ptko_` handle, and reads the payload back through
  `ptk_output`.
- `WorkerPrivateHostRuntimeTests.Job_terminal_seals_the_retained_background_output_capture`
  — the in-proc rig guard on the wiring itself: the capture is retained
  unsealed across the job's life and sealed with the worker's own job output
  when the terminal arrives.

Mutation-proven on macOS, each mutation red on its own:

| mutation | composition guard | rig guard |
|---|---|---|
| capture created but never registered in `JobCaptures` | red | red |
| terminal never calls `SealBackgroundJobOutput` | red | red |
| seal the fetched text as `string.Empty` | red — pins the content assertion, which the handle assertion alone would not | (not run; the rig guard asserts the same content) |

Restored: green.

**Test-fake change, and why it was not a bypassed roadblock.**
`RecordingOutputTransfer.CreateExecutionCapture` in the rig previously threw
`"Worker runtime cannot create an in-process capture owner."`, so the fix made
four existing rig tests refuse every background invoke. That throw is not a
product invariant: `git log -S` places it in `1e19b46`, the same cutover commit
that dropped the background capture, so it records the defect's own assumption
rather than a constraint. It is also factually wrong about the real collaborator
— `EventPrivateHostOutputTransfer` is event-based, emitting guardian chunk/seal
events from the private host, with nothing in-process about it. Replaced with a
recording capture owner that models the real one.

**Stale-binary trap, recorded because it cost a cycle.** Restoring the product
file with `Copy-Item` read red on a clean tree: `Copy-Item` preserves
`LastWriteTime`, so MSBuild saw the source as older than the mutated binary and
skipped the rebuild. This is the same trap the #1 reviewer defeated with an
explicit mtime touch. Any mutation loop that restores by copy must touch the
file afterwards.

### Approach

Restore a background execution capture in `WorkerPrivateHostRuntime`, mirroring
what `DefaultPrivateHostRuntime` + `JobManager` do today:

1. `ExecuteBackgroundAsync` creates the capture from the request, prepares it
   against the request deadline (which is also the output capability's expiry —
   both come from `admitted.DeadlineUnixTimeMilliseconds`,
   `GuardianHostSupervisor.cs:522-525`), and on a started job transfers it to
   background and retains it per alias beside the job capability.
2. The existing job-terminal hook `ReleaseJobTerminal` (already wired through
   `PrivateHostWorkerEventBridge.JobTerminalObserved`) takes the retained
   capture, fetches the job's output from the worker, and seals it.

The fetch must go straight to `slot.Process.ExecuteAsync` (its `beforeWrite`
callback is optional, `WorkerProcessClient.cs:31-36`) rather than through
`ExecuteOrdinaryAsync`: delivery events record guardian-issued requests, and a
host-internal fetch has no guardian request id to report. Sealing must not run
inline on the terminal callback, which holds both the bridge's and the runtime's
lock — use the fire-and-forget shape `ContainAfterExecutionTimeout` already
establishes.

**These tests were almost certainly never green under the worker runtime.**
They are Windows-gated, so they never ran on the macOS or Linux hosts used for
R6, and Windows evidence was outstanding until this session.

Note the swallowing `catch` at `GuardianOutputCapabilityRegistry.cs:137-140`
converts any exception into a bare `"output_store_unavailable"` with no
diagnostic. It is not implicated here, but it is the same anti-pattern that hid
`r6x-1` for a full session and is worth its own cleanup.

## Approach

For #1, not yet authored. The shape is to make an unrepaired `RecoveryUnknown`
**sticky** in `FrozenDefaultSessionState`: a Ready lifecycle event arriving for
an alias in that condition must not silently restore it to usable, and only an
explicit repair (reset/reopen) may clear it. The care needed is in not
breaking the legitimate `RecordAcknowledgedReady` initial-ready path or the
automatic-recovery ready path, both of which also arrive as Ready lifecycles.

## Diagnosis of #2 (never replays a real effect) — 2026-07-25

**A stale test expectation from before the R6 worker cutover. Not a product
defect, and not Windows-specific — the third of these in one finding.**

The identity waited on
`launcher.ReplacementHostProcessId` and asserted `LaunchCount == 2` and host
generation 2. After the cutover an ambiguous worker death is recovered by
replacing **the alias's worker**, not the private host, so that wait never
completes and the test burns its whole 60-second budget — which is exactly the
bare `TaskCanceledException` with no assertion failure that made it look
mysterious.

Measured with the same probe on both platforms (saved as
`r6x-2-no2-probe.patch`), and the two are identical:

```
R6X2_AMBIGUOUS>>>OutcomeUnknown retryable=False launchCount=1
R6X2_RECOVERED>>>attempt=7 hostState=Ready hostGen=1 warmLost=True
                 sessionState=Ready workerGen=3 launchCount=1
R6X2_REINVOKE>>>effect-was-not-replayed
```

The host is never relaunched (`launchCount=1`, `hostGen=1`), the worker
generation advances, warm state is correctly reported lost, the ambiguous call
is `outcome_unknown` and non-retryable, and the follow-up invoke runs exactly
once. **The invariant the test exists to protect — an ambiguous effect is never
replayed — holds.**

A second, quieter bug in the same test: it polled **host** readiness and then
immediately dispatched an effect. The host is ready before the alias is, so the
follow-up invoke could race a `Starting` session and be refused. Readiness is
now polled on the session, which is what actually decides whether an effect can
be dispatched.

### Repair

- Renamed to `Composition_never_replays_a_real_effect_when_the_worker_dies`:
  the host does not die, the worker does.
- **Un-gated from Windows.** The behaviour is identical on both platforms, and
  Windows-gating is precisely what hid all three defects in this finding for an
  entire release cycle.
- Asserts per-alias worker recovery — host generation stays 1, session returns
  to `Ready` on an advanced worker generation, warm state lost — instead of host
  replacement, and re-checks host generation after the follow-up invoke so a
  silent host relaunch would still fail the test.
- Every no-replay assertion is unchanged.

### Guard proof (#2) — not applicable, and why

There is **no product change to revert**, so the revert → FAIL → restore → PASS
proof does not apply and claiming one would be dishonest. Reverting the repair
does redden the identity, but only by restoring the 60-second hang — that proves
the test changed, not that a defect was closed.

The manual check that stands in its place is the probe above, run on **both**
macOS and Windows and producing identical readings. It is what establishes the
claim the repair rests on: the private host is never relaunched, per-alias
worker recovery is what happens, and the no-replay invariant holds. The probe is
saved as `r6x-2-no2-probe.patch` so the reading can be reproduced rather than
taken on trust.

**This is the part of #2 most worth a reviewer's scrutiny.** The repair changes
what an existing R5 acceptance identity asserts, on the argument that the R6
worker cutover made host replacement obsolete. If that argument is wrong, the
repair pins a real regression as correct behaviour, and no guard proof would
catch it — only judgment about intended architecture will.

## Guard proof (#1)

The pre-existing `Ambiguous_lifecycle_stays_blocked_until_an_authoritative_repair`
covered only `ObserveHostReady` — **not** the `SessionLifecycleEvent` channel
that actually carries a replacement host's restored session. That is why the
defect shipped past a test whose name claims to cover it. Two new guards close
the gap, and both are platform-neutral, so unlike `r6x-1` this proof runs
anywhere:

- `Ready_lifecycle_cannot_repair_an_ambiguous_alias` — a Ready lifecycle leaves
  the alias blocked, still absorbs the new worker identity, and an
  authoritative result then repairs it.
- `Repaired_alias_accepts_an_ordinary_ready_lifecycle_again` — stickiness ends
  at the repair, so automatic recovery can still bring the alias back.

Mutation-proven on macOS, each mutation reddening only its own guard:

| mutation | red |
|---|---|
| interception removed | `Ready_lifecycle_cannot_repair_an_ambiguous_alias` |
| flag never armed | same |
| repair never clears the flag | `Repaired_alias_accepts_an_ordinary_ready_lifecycle_again` |

Baseline and restored runs both green (3/3).

Two points where it verified something the fix had only reasoned about:

1. **Clearing only in `ObserveSessionOperationResult` is provably the explicit
   repair channel.** Its sole production caller
   (`GuardianHostSupervisor.cs:3224`) is gated on a correlated success terminal,
   and `IsSessionChangingOperation` (`:3611-3616`) covers only
   Reset/SessionOpen/SessionClose/SessionRestart — all explicit operator
   actions, none emitted by automatic recovery. So "authoritative
   session-changing result" and "explicit repair" are the same set here, and
   clearing unconditionally is right because a known outcome ends ambiguity by
   definition.
2. **Absorbing the worker identity while blocked is not merely safer — the
   alternative wedges.** Ignoring the Ready event entirely would leave
   `state.WorkerIdentity` naming the dead worker, and
   `ObserveSessionOperationResult`'s binding check (`:441-447`) would then throw
   on the repair result targeting the live worker, blocking the alias
   permanently.

Also confirmed: the interception sits after all lifecycle validation, so a
malformed Ready event still throws (read, not assumed); Cold/Faulted are not a
hole, since neither touches the flag and any later Ready is still intercepted;
no stuck/wedge path exists; and the pre-existing
`Ambiguous_lifecycle_stays_blocked_until_an_authoritative_repair` still means
what it claims — it covers the `ObserveHostReady` channel, which was never the
hole.

has no equivalent stickiness, but its `ObserveSessionLifecycle` is a no-op so it
