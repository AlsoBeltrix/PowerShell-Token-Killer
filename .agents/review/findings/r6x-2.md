# r6x-2: three `Windows_*` real-composition tests fail for a non-audit reason

**Severity**: HIGH — these are three of the six real-apphost Windows identities
R6's acceptance matrix must prove (`.agents/plans/mcp-resilience.md`, R6
sub-slice 6). While they fail, R6 cannot be claimed cross-platform complete and
R7 cannot start on a proven Windows baseline.
**Status**: Open — evidence captured, cause not yet diagnosed
**Branch**: (none)
**Commit**: (none)

## Evidence

All three fail on `NETWATCH-01` at head `168905c` (Windows NT 10.0.26200.0 x64,
.NET SDK 10.0.302, ordinary identity), and all three pass on Linux ARM64 at the
same head. Guardian is 480/484 with exactly these three plus `r6x-3`.

1. `ProductionGuardianCompositionTests.Windows_composition_requires_explicit_repair_after_ambiguous_reset`
   — `Assert.Equal` expected `RecoveryUnknown`, actual `Ready`, at
   `ProductionGuardianCompositionTests.cs:1223`.
2. `ProductionGuardianCompositionTests.Windows_composition_never_replays_a_real_effect_when_the_host_dies`
   — `System.Threading.Tasks.TaskCanceledException` after ~1 minute, at
   `ProductionGuardianCompositionTests.cs:2138`.
3. `ProductionGuardianCompositionTests.Windows_composition_keeps_a_real_job_tombstone_and_sealed_output`
   — "The background job did not publish a sealed terminal. Last status: job 1:
   exited 0, output completeness unknown, ... recovery=unavailable: output
   capture unavailable", at `ProductionGuardianCompositionTests.cs:1865`.

## Predicted observable failure

Already observed — these are live failures, not a predicted risk. What is not
yet established is the mechanism, and whether the three share one.

## What

These were originally lumped into `r6x-1` on the theory that one degraded audit
subsystem explained all four `Windows_*` composition failures. Fixing `r6x-1`
disproved that: its sibling `..._classifies_real_prewrite_loss` now passes,
because that one genuinely did fail through `audit=unavailable`. These three
kept their original signatures — a wrong session state, a timeout, and an
unavailable output capture — none of which is the audit-degradation signature.
So one or more separate Windows-specific defects remain.

## Approach

Not authored. Diagnosis should start by establishing whether the three share a
cause. Note that #3's "output capture unavailable" and #1's wrong session state
both smell like a Windows-side supervisor/worker behaviour gap rather than one
shared root, so treat "they are all one bug" as a hypothesis to test, not an
assumption — that assumption is exactly what went wrong the first time.
