# r6x-2: three `Windows_*` real-composition tests fail for a non-audit reason

**Severity**: HIGH — these are three of the six real-apphost Windows identities
R6's acceptance matrix must prove (`.agents/plans/mcp-resilience.md`, R6
sub-slice 6). While they fail, R6 cannot be claimed cross-platform complete and
R7 cannot start on a proven Windows baseline. Raised further by the #1
diagnosis below: that one is a live correctness defect, not a test problem — an
ambiguous reset leaves the session projecting usable, so work can be dispatched
into a session whose outcome is unknown.
**Status**: Open — #1 root-caused (fix not authored), #2 and #3 reproducible
but undiagnosed
**Branch**: (none)
**Commit**: (none)

## Predicted observable failure

Already observed — these are live failures, not a predicted risk. What is not
yet established is the mechanism, and whether the three share one.

## What

These were originally lumped into `r6x-1` on the theory that one degraded audit
subsystem explained all four `Windows_*` composition failures. Fixing `r6x-1`
disproved that: its sibling `..._classifies_real_prewrite_loss` now passes,
because that one genuinely did fail through `audit=unavailable`. These three
kept their original signatures — a wrong session state, a timeout, and an
unavailable output capture — none of which is the audit-degradation signature.
So one or more separate Windows-specific defects remain.

## Diagnosis of #1 (ambiguous reset) — root cause found 2026-07-25

**An ambiguous session outcome is silently erased by the replacement host's
declared-session restoration, permanently.** It is not a timing race in the
test.

Measured on `NETWATCH-01` at head `3ecc86f` with a throwaway probe that keeps
polling `ptk_state` after the point where the test asserts. Across 61 samples
spanning 6 seconds the session never changes:

```
t0  hostReady=True hostGen=2 sess=Ready warmLost=True boot=Restored
...
t60 hostReady=True          sess=Ready warmLost=True boot=Restored
```

`boot=Restored` is the tell: `BootstrapState.Restored` is only ever written by
the Ready branch of `FrozenDefaultSessionState.ObserveSessionLifecycle`
(`FrozenDefaultSessionState.cs:335-353`, committed at `:391-394`). So the
sequence is:

1. The ambiguous `ptk_reset` makes `GuardianHostSupervisor` call
   `ObserveSessionRecoveryUnknown` (`GuardianHostSupervisor.cs:2431` or
   `:3232`), which sets the alias to `RecoveryUnknown`, `ReadyForEffects=false`,
   `BootstrapState=Unknown` (`FrozenDefaultSessionState.cs:398-414`).
2. The lost host is replaced, and the replacement's declared-session
   restoration emits a **Ready** `SessionLifecycleEvent`.
3. `ObserveSessionLifecycle`'s Ready branch overwrites `State`,
   `ReadyForEffects` and `BootstrapState` unconditionally. Nothing consults
   whether the alias is sitting in an unrepaired `RecoveryUnknown`.
4. Nothing ever restores it, so the alias projects `Ready` and
   `ReadyForEffects=true` for the rest of the session.

Confirmed structurally: `RecoveryUnknown` appears in
`FrozenDefaultSessionState.cs` at exactly two lines — the method at `:398` and
its assignment at `:409`. There is no stickiness, no repair gate, and no
guard on the Ready path.

**Why this matters beyond a red test.** The snapshot type enforces
`readyForEffects == (state == Ready)`
(`PtkSharedContracts/Public/PublicState.cs:152`), so the alias does not merely
look wrong — it is projected as fully usable. R6's contract is that ambiguity
becomes `recovery_unknown` and that ordinary session work stays blocked until
an explicit lifecycle result repairs the alias
(`.agents/plans/mcp-resilience.md`, R6 sub-slice 5;
`GuardianHostSupervisorContracts.cs:206-212`). A model can therefore dispatch
work into a session whose reset outcome is unknown — the exact no-replay
boundary the design exists to protect.

**Inferred, not proven: macOS passes by ordering luck rather than by
protection.** The product has no guard on either platform; the plausible
reading is that on macOS the ambiguous marking happens to be committed after
the ready lifecycle and therefore survives, while on Windows the replacement
completes first and overwrites it. Confirming that needs the same probe run on
macOS, which has not been done. Either way the invariant is unenforced
everywhere, so this should not be treated as Windows-specific behaviour.

## Approach

For #1, not yet authored. The shape is to make an unrepaired `RecoveryUnknown`
**sticky** in `FrozenDefaultSessionState`: a Ready lifecycle event arriving for
an alias in that condition must not silently restore it to usable, and only an
explicit repair (reset/reopen) may clear it. The care needed is in not
breaking the legitimate `RecordAcknowledgedReady` initial-ready path or the
automatic-recovery ready path, both of which also arrive as Ready lifecycles.

For #2 and #3, still undiagnosed. Both fail deterministically (2 of 2 isolated
runs each at `3ecc86f`), so neither is a flake and both are directly
reproducible. Do NOT assume they share #1's cause: #1 turned out to be a
guardian declared-state ordering defect, whereas #3's "output capture
unavailable" points at the supervisor-owned output store and #2 is a plain
60-second timeout. Treating the group as one bug is what produced the original
`r6x-1` mis-attribution.
