# r6x-3: `State_polling_is_guardian_local_and_scheduler_inert` is nondeterministic on Windows

**Severity**: MEDIUM — a mostly-failing test on Windows. It blocks a clean
Windows Guardian run (so it will block R6's acceptance matrix and any Windows CI
leg), but it is a test-determinism defect, not a proven product defect.
**Status**: **Fixed and verified on Windows, 2026-07-25.** The
test-determinism hypothesis below was correct; the mechanism is recorded under
"Root cause".
**Branch**: `feature/mcp-resilience-r1`
**Commit**: see the settle-before-baseline fix in
`GuardianHostSupervisorTests`

## Root cause (2026-07-25)

**The test captures its baseline before startup has finished scheduling.** It
is not a product defect and the assertion was pinning the right thing.

`State_polling_is_guardian_local_and_scheduler_inert` records
`rig.Scheduler.ScheduleCount` on the line after `StartAsync()` returns, then
asserts the count is unchanged after 100 guardian-local state reads. But the
supervisor issues **two** scheduler delays during startup, and the second can
land after `StartAsync()` returns.

Measured directly on `NETWATCH-01` with a throwaway probe that performed **no
polling at all** — same rig, same start, 40 samples 25 ms apart:

```
run 1: 2,2,2,2, ... ,2      (already settled before the first sample)
run 2: 2,2,2,2, ... ,2
run 3: 1,2,2,2, ... ,2      (second startup schedule landed within 25 ms)
```

The count never moves again afterwards. Since no state read occurred in that
probe, polling is exonerated outright: when the baseline happens to be taken at
`1`, the later startup schedule makes it `2` and the assertion fails having
measured startup rather than polling. Windows timing loses that race far more
often, which is exactly the observed ~4-of-5 rate; macOS and Linux usually
settle before the capture, which is why the identity passes there.

## Fix

`SettledScheduleCountAsync` waits for the schedule count to hold steady across
five consecutive 25 ms samples before the baseline is taken. The assertion
itself is untouched — it still demands *exact* equality after the 100 reads, so
the guard continues to pin "guardian-local reads schedule nothing". The
`Approach` section's warning was followed: the assertion was **not** loosened to
accept 2.

The sibling `Public_session_list_is_guardian_local_and_uses_projected_state`
captures its baseline identically and gets the same treatment. It has not been
observed failing, so that is luck rather than immunity.

## Verification

On `NETWATCH-01` (Windows), disposable checkout at `fc93227`:

- Before the fix: **4 of 5** isolated runs failed, reproducing the recorded rate.
- After the fix: **10 of 10** isolated runs passed.
- Guard proof: removing only the settle and rebuilding returned it to **4 of 5**
  failing; restoring it returned **0 of 5** failing.
- macOS: both identities pass.

## Predicted observable failure

Already observed. The assertion counts something expected to happen exactly
once and observes it twice, so the likely mechanism is an unsynchronised extra
poll or scheduler tick that Windows timing exposes far more often than
macOS/Linux — where the identity passes.

## What

The test asserts that state polling stays guardian-local and leaves the
scheduler inert. On Windows it usually observes two of whatever it counts
instead of one. Because it is ~80% failing rather than a rare flake, it is
tractable to diagnose directly rather than by long repetition.

## Approach

Not authored. Read the assertion's subject at
`GuardianHostSupervisorTests.cs:2267` and establish whether the second
observation is a genuine duplicate poll in the product or an unsynchronised
observation in the fixture. Do not "fix" it by loosening the assertion to accept
2 — that would discard whatever the guard exists to pin. If the extra
observation turns out to be real product behaviour, this becomes a product
finding rather than a test-determinism one.
