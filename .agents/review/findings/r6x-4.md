# r6x-4: `Unix_out_of_range_second_descriptor_closes_first_owned_descriptor` races file-descriptor reuse

**Severity**: LOW — a rare flake in a loaded full-suite run. It is a
test-determinism defect, not a product defect: the behaviour under test is
correct, only the way the test observes it is unsound. It costs a false red on
CI and erodes trust in the suite.
**Status**: Open — diagnosed, not fixed. The diagnosis is a strong mechanism
argument, not a reproduction; see "Known gaps".
**Branch**: `feature/mcp-resilience-r1`
**Commit**: none.

## Evidence

`PtkMcpServer.Tests.PrivateHostBootstrapTests.Unix_out_of_range_second_descriptor_closes_first_owned_descriptor`
failed once during a full `dotnet test server/PtkMcpServer.slnx` run on macOS
(2026-07-26, around head `1a5ffaf`) and passes in isolation. It was green in the
immediately preceding and following full runs, so it is intermittent and rare.

## What

The test proves that when the second inherited descriptor is out of range, the
bootstrap closes the first descriptor it had already taken ownership of. It
observes that closure at `PrivateHostBootstrapTests.cs:598`:

```csharp
Assert.Equal(-1, TestNativeMethods.GetDescriptorFlags(requestRead, TestFGetFd));
```

`requestRead` is a raw `int` file descriptor. The assertion says "this fd number
is no longer valid", which is a sound proxy for "it was closed" only while
nothing else in the process can acquire that number.

## Predicted observable failure

`GetDescriptorFlags` returns a non-negative value instead of `-1`, because
between the close and the assertion some other thread in the same process
opened a file, pipe, or socket and the kernel handed back the lowest free
descriptor — the very number just released. The product did exactly the right
thing; the test then reports it did not.

Conditions that make it possible, all confirmed in this repo:

- `PtkMcpServer.Tests` has no `xunit.runner.json`, no `[Collection]` on this
  class, and no `DisableTestParallelization`, so xUnit's default cross-class
  parallelism applies and other classes run concurrently in-process.
- Those classes open descriptors heavily — they launch real host and worker
  processes, create pipes, and write fixture files.
- POSIX `open`/`pipe` allocate the lowest available descriptor number, so a
  freshly freed number is the *first* candidate for reuse, not a remote one.

That combination is exactly "rare, only under a loaded full-suite run, never in
isolation", which is the observed signature.

## Approach

Do not fix this by disabling parallelism: the runtime itself opens descriptors,
so serialising the suite narrows the window without closing it, and it would
slow every run to paper over one assertion.

Make the observation reuse-proof instead. Two candidates, neither yet
implemented:

1. **Observe the peer end.** Hold the write end and assert that writing to it
   fails with `EPIPE` once the read end is closed. Descriptor numbering is
   irrelevant to that signal.
2. **Compare identity, not validity.** `fstat` the descriptor before the call,
   and afterwards assert the number is either invalid *or* no longer refers to
   the same pipe (`st_dev`/`st_ino` differ). This keeps the current shape and
   needs one more P/Invoke.

Option 1 is simpler and tests the property more directly. Option 2 preserves the
existing assertion's letter.

## Guard proof

Not applicable yet. Note that a guard proof for this fix is awkward by nature:
the failure is a rare race, so "reverting the fix makes it fail" cannot be shown
on demand. The honest proof is that the repaired assertion no longer depends on
descriptor numbering at all — an argument about the observation's soundness
rather than a red-to-green demonstration. State that plainly when fixing rather
than claiming a proof the change cannot support.

## Known gaps

- **Not reproduced.** The mechanism argument is strong and every precondition is
  confirmed, but the race was observed once and not reproduced on demand. Treat
  the cause as a well-supported hypothesis, not an established fact, until
  either it recurs with the failure message captured or the repaired assertion
  is shown to be numbering-independent by construction.
- The failing assertion was identified from the test source, not from a captured
  failure message — the run recorded only the identity. If it recurs, capture
  the message first; if it is *not* line 598, this diagnosis is wrong.
