# r6x-5: the real-apphost readiness poll is budgeted in attempts, not time, and exhausts under full-suite load

**Severity**: MEDIUM — a false red on the R6 acceptance matrix's flagship
recovery line, on the platform the matrix requires and on the core count hosted
CI runners actually have. It is a test-determinism defect, not a product defect:
the behaviour under test is correct and was proven correct on the same host.
**Status**: **Fixed 2026-07-26.** The budget is now wall clock, which does not
shrink under load, so the exhaustion this finding describes is gone by
construction.
**Branch**: `feature/mcp-resilience-r1`
**Found at**: `3fdbbff`

## Fix

All eleven poll sites now share one wall-clock budget instead of counting
attempts:

```csharp
private static readonly TimeSpan ReadinessPollBudget = TimeSpan.FromSeconds(30);

private static bool PollingWithinBudget(long pollStarted) =>
    Stopwatch.GetElapsedTime(pollStarted) < ReadinessPollBudget;
```

Each site's loop header becomes
`for (var pollStarted = Stopwatch.GetTimestamp(); PollingWithinBudget(pollStarted);)`.
Bodies are untouched: each keeps its own `await Task.Delay(25, timeout.Token)`,
so the poll cadence is unchanged and only the stopping rule moved. The `400`
special case is gone — it was the same cliff moved once, and one budget now
covers every site.

The eight identities that poll also needed an enclosing deadline able to contain
that budget, or a poll that never succeeds would surface as an opaque
`OperationCanceledException` from the body's delay instead of failing on its own
assertion. They now share `PollingTestTimeout` (180 s), sized for the three
identities that poll twice. It bounds only pathological hangs; a healthy run
reaches each condition in well under a second.

## Guard proof

Not red-to-green on the original race — as with `r6x-4`, a load-induced
exhaustion cannot be summoned on demand, and claiming otherwise would be
dishonest. The proof is that the budget is load-bearing and the assertions are
non-vacuous: setting `ReadinessPollBudget` to 1 ms and rebuilding reddens
**3 of the 15** composition identities on macOS —
`Unix_composition_recovers_real_host_and_descendants_on_the_same_public_connection`,
`Composition_seals_a_real_background_job_artifact_for_handle_recovery`, and
`Composition_never_replays_a_real_effect_when_the_worker_dies` — each failing on
its own assertion rather than a cancellation. Restoring 30 s returns the class
to 15/15 and the assembly to 496/496.

That exactly 3 of the 8 polling identities redden is itself corroboration of
audit finding F1: the other five are Windows-gated and return vacuously on
macOS, so no budget change can move them there. They need a Windows run to be
proven at all.

The structural half of the argument: a budget counted in wall clock cannot be
exhausted by round trips getting slower, because it is not counted in round
trips.

**Linux verification of the fix.** On `magneto`,
`Unix_composition_recovers_real_host_and_descendants_on_the_same_public_connection`
— the identity this finding was opened on — passed every post-fix run. The
poll-exhaustion failure has not recurred.

## Second defect found by verifying the first

Re-running the Linux assembly with the poll fix in place exposed a second fixed
budget of the same family, in a test with **no poll site at all**:
`Composition_isolates_one_alias_worker_crash_from_a_second_alias` failed **3/3**
against the class's old 30 s `TestTimeout`, while every other identity passed.
It starts two real workers, crashes one, and observes recovery — the heaviest
identity in the file — and 30 s was a number chosen against a fast development
Mac.

Fixed by giving the whole class one deadline: all twelve identities now share
`CompositionTestTimeout` (180 s), since every one of them launches real
guardian, host, and worker processes and is exposed to the same host-load
effects. One deadline per class is far less likely to rot into per-test tuning
than the previous mix of 30 s, 45 s, and 60 s. The 30 s constant survives only
as `BrokerCompileTimeout`, renamed so it cannot be mistaken for a test deadline
again. Verified: the identity that failed 3/3 now passes.

## Residual: the assembly does not fit this host — NOT part of this finding

With both budget defects fixed, the Linux guardian assembly is **still not
green**, and the remaining failures are environmental rather than defects:

| Configuration | Result |
|---|---|
| Default parallelism, 3 runs | 495/496 each, a **different** test each run |
| Default parallelism, 2 more runs | 495/496 and 494/496, different tests again |
| `-maxthreads 2`, 2 runs | 495/496 both, the same test each time |
| Any of the above tests run alone | Passes 3/3, in 0.4-0.6 s for the rig tests |

The assembly self-saturates a 4-CPU host — it drives load to ~7 even when
started at 1.5 — and roughly one timing-sensitive test loses per run. Every
individual loser passes in isolation, so no product behaviour is implicated.
This is the R5 Linux record's warning recurring at assembly scope rather than
battery scope: that record's remedy, "one MSBuild project at a time and no
competing workload", is not sufficient, because xUnit also parallelizes *within*
the assembly.

Do not chase this one test at a time — that is whack-a-mole, and this finding
already spent two rounds proving the pattern. It needs a decision about how the
guardian assembly is scheduled on constrained hosts, which is also the shape of
a hosted `ubuntu-latest` runner. Recorded as an open question rather than fixed,
because capping parallelism costs wall clock on every host and that is not a
call to make silently.

## Evidence

`PtkMcpGuardian.Tests.ProductionGuardianCompositionTests.Unix_composition_recovers_real_host_and_descendants_on_the_same_public_connection`
failed once during the full guardian assembly on x64 Linux `magneto` (4 CPUs,
load average 5.5-8.4 during the run), taking Guardian to 495/496. Everything
else in that battery passed: architecture 73/73, server 2,044/2,044, Pester
141 with 2 expected skips, complete stdio handshake. Full context is in
`.agents/machines.md` under "R6 acceptance battery on x64 Linux `magneto`".

The failure is `Assert.NotNull(recovered)` at
`ProductionGuardianCompositionTests.cs:1158`.

**The same identity passes 3/3 on the same host in isolation** once the box is
idle — 15.6 s, 17.0 s, 16.8 s. So the recovery path itself works on Linux: real
host killed, containment confirmed, descendants and cold-background job reaped,
replacement launched at generation 2, warm state reported lost, and a real
`ptk_invoke` served on the same public connection.

## What

After killing the real host and confirming containment, the test polls
`ptk_state` for readiness:

```csharp
for (var attempt = 0; attempt < 200; attempt++)
{
    var response = await RequestAsync(writer, reader, requestId++, "tools/call",
        new { name = "ptk_state", arguments = new { } }, timeout.Token);
    var candidate = PublicStateCodec.Decode(...);
    if (candidate.Host.ReadyForEffects) { recovered = candidate; break; }
    await Task.Delay(25, timeout.Token);
}
Assert.NotNull(recovered);
```

The budget is **200 attempts**, not a wall-clock deadline. Each attempt is one
full MCP request/response round trip plus a 25 ms delay, so the elapsed budget
is whatever 200 round trips happen to cost. On an idle host that is a few
seconds and recovery finishes with enormous margin. Under full-suite
saturation, launching and bootstrapping a replacement .NET apphost is slow at
exactly the same time as the round trips are slow, and the attempt count runs
out before readiness arrives.

Note the outer `timeout.Token` did **not** fire — a cancellation would have
surfaced as `OperationCanceledException`, not a null assertion. This is the
attempt budget alone.

## Scope — this is not one test

The same `attempt < 200` readiness-poll shape appears at **eleven** sites across
**seven** real-apphost composition identities:

| Line | Identity |
|------|----------|
| 146 | `Composition_seals_a_real_background_job_artifact_for_handle_recovery` |
| 1105, 1140 | `Unix_composition_recovers_real_host_and_descendants_on_the_same_public_connection` |
| 1523 | `Windows_composition_retains_real_decoded_terminal_on_loss` |
| 1709 | `Windows_composition_requires_explicit_repair_after_ambiguous_reset` |
| 2077 | `Windows_composition_recovers_a_real_host_on_the_same_public_connection` |
| 2183, 2211 (400) | `Windows_composition_recovers_after_replacement_dies_during_startup` |
| 2347, 2477 | `Windows_composition_keeps_a_real_job_tombstone_and_sealed_output` |
| 2671 | `Composition_never_replays_a_real_effect_when_the_worker_dies` |

Only one site has ever been raised to 400, and only for the
replacement-dies-during-startup case — evidence that the budget has already been
found too small once and was widened locally rather than fixed in kind.

Every one of these is an R6 acceptance identity. The Unix one failed first only
because Linux is the first 4-CPU host to run the full guardian assembly on this
branch; macOS and `NETWATCH-01` both have more cores and more headroom.

## Why this matters beyond the flake

`.github/workflows/ci.yml` runs this assembly on `ubuntu-latest`, whose standard
hosted runners are 2-4 cores — the same shape as `magneto`, not the shape of the
development Macs. This is a latent hosted-CI flake in the acceptance suite, and
it will present as a recovery regression rather than as a timing artifact.

## Approach

Not authorized; recorded so the fix is not redesigned from scratch.

Replace the attempt count with a wall-clock deadline on the same
`timeout.Token`-derived clock, so the poll is bounded by elapsed time rather
than by how many round trips fit. A shared helper — `PollUntilReadyAsync(...)`
with one budget constant — should own all eleven sites, so the budget is
tunable in one place and the 400 special case disappears.

Do **not** fix this by disabling parallelism: it would slow every run and the
composition tests launch real processes whose cost is not under xUnit's control
anyway.

Do **not** simply raise 200 to a larger number. That repeats the 400 patch: it
moves the cliff without removing it, and leaves the budget expressed in a unit
(round trips) that varies with load by exactly the factor that causes the
failure.

## Guard proof

Awkward by nature, and the honest claim should be stated as such rather than
overclaimed — the same shape as `r6x-4`. A load-induced exhaustion cannot be
summoned on demand. Two defensible proofs:

1. Set the new deadline constant to something absurdly small (say 50 ms) and
   confirm every converted site reddens; restore and confirm green. This proves
   the budget is load-bearing and the assertion non-vacuous.
2. Confirm the converted identity still fails when the product genuinely never
   recovers — e.g. suppress the replacement launch — so the test still
   distinguishes "slow" from "broken".

Neither proves the original race is gone; the argument for that is structural,
as it was for `r6x-4`: a time budget cannot be exhausted by round trips getting
slower, because it is not counted in round trips.

## Known gaps

- **Reproduced once.** The mechanism argument is strong and the isolation runs
  are clean 3/3, but the failure was observed a single time. If it recurs,
  capture the load average and the elapsed time to exhaustion — if exhaustion
  happens fast on an idle box, this diagnosis is wrong and the recovery path is
  genuinely at fault.
- The ten sites other than line 1140 have **not** been observed failing. They
  are named here because they share the defective shape, not because each has
  its own evidence.
