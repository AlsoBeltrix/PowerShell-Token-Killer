# r7-1: the guardian goes audit-unavailable against an existing audit root, so the R7 cutover would brick a live install

**Severity**: HIGH — this is an upgrade-path defect, not a test defect. After the
R7 cutover the owner's ptk would start, answer `initialize`, list all six tools,
and then refuse **every** effect with `[operation not started] Required audit
persistence is unavailable`. The tool looks alive and does nothing.
**Status**: **Open, reproduced 2026-07-26.** No fix attempted.
**Branch**: `feature/mcp-resilience-r1`
**Found at**: `c618ac3`

## What happens

Point the packaged guardian at an audit root created by the currently installed
(pre-guardian) server and it comes up degraded:

```
audit=unavailable
unrecorded=true
failure_class=evidence.storage
protection_mode=local-only
spool_bytes=0
```

Every `ptk_invoke` then returns `[operation not started] Required audit
persistence is unavailable; the original operation was not started.` Audit is
mandatory and fails closed by design, so this is the designed response to a
storage the runtime will not accept — the defect is that it will not accept a
perfectly ordinary existing root.

## Trigger, isolated

Against copies of the real `~/.ptk/audit`, removing one component at a time:

| Root | Result |
|---|---|
| fresh, empty | **works** |
| guardian's own root, second run | **works** |
| real root, `evidence/` removed | **works** |
| real root, `spool/` removed | **fails** |
| real root, both removed | **works** |

So the trigger is the **`evidence/` directory**, and nothing else.

`~/.ptk/audit/evidence` on this machine holds **12 orphaned `.script` files**
left by previous boots of the installed server, with no owning boot record. That
is exactly the shape
`AuditEvidenceOrphanReconcilerTests.Local_runtime_stays_diagnostic_only_without_sweeping_incomplete_history`
describes: the local runtime deliberately stays diagnostic-only rather than
sweeping history it did not write. Diagnostic-only means `audit=unavailable`,
and because audit is mandatory, that means every effect refuses.

## Why this blocks R7

R7 replaces the registered binary with the guardian and reuses the same
`~/.ptk` home, including `~/.ptk/audit`. Any machine with accumulated orphan
evidence — which is the normal state of a machine that has been running ptk —
gets a guardian that cannot do anything. The plan's cutover requires rollback on
failed *activation or registration*, and this failure is neither: activation and
registration both succeed. The install reports success and the tool is inert.

## What is not yet known

- Whether a **cleanly stopped** old server leaves orphan evidence. The 12 files
  here accumulated under normal use, and the installer's
  `Assert-PtkServerNotRunning` only guarantees no *live* writer, not a swept
  evidence directory. An attempt to reproduce a clean-shutdown root failed to
  reproduce the setup: the old server, run against a fresh `PTK_AUDIT_ROOT`,
  left that root **empty**, so it never produced the orphan state to test.
- Whether the guardian is *supposed* to adopt a pre-existing local evidence
  directory at all, or whether the cutover is supposed to migrate or retire it.
  That is a design question for the plan, not something to guess at in code.

## Approach

Not authorized, and it should not be chosen without settling the design
question above. The plausible options, in the order they should be considered:

1. **Cutover-time migration.** The installer retires or archives the prior
   evidence directory as part of the payload snapshot it already takes, so the
   guardian starts against evidence it owns. Fits the existing rollback story:
   the snapshot already exists and restoring it restores the old state.
2. **Adoption at startup.** The local runtime sweeps or claims orphan evidence
   it finds in local-only mode. This changes deliberate audit semantics and
   needs to be argued against the orphan-reconciler tests before anyone touches
   it, because those tests encode a decision, not an accident.
3. **Loud refusal.** Detect the condition during cutover and fail the install
   with remediation, instead of shipping a running-but-inert tool. Weakest
   outcome, but strictly better than the current silent failure and it is the
   pattern the repo already uses for the Defender-quarantine case.

Whatever is chosen, the cutover must gain a check that the guardian reaches
`audit=available` against the **actual** target audit root before registrations
are mutated. That check is missing today and is what let this reach the field
untested.

## Evidence

Reproduced with the packaged layout built by
`scripts/dev-install.ps1 -LayoutOnly`, driving the real guardian binary over
stdio: `initialize` succeeds, `tools/list` returns all six tools
(`ptk_invoke`, `ptk_job`, `ptk_output`, `ptk_reset`, `ptk_session`, `ptk_state`),
and `ptk_state` reports the degraded block above. The same binary against a
fresh root returns `guardian-live-4` with a working `ptk_output` handle, so the
guardian itself is sound.
