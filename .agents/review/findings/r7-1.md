# r7-1: upgrading across the evidence filename change leaves ptk running and totally inert

**Severity**: HIGH — not an R7 or guardian defect, as first filed. **Any** current
build, guardian or plain server, refuses to run against an audit root written
before 2026-07-11. The process starts, answers `initialize`, lists every tool,
and then refuses **every** effect with `[operation not started] Required audit
persistence is unavailable`. Install and registration both succeed, so nothing
rolls back and nothing reports a problem.
**Status**: **Fixed for the install path 2026-07-26** (`Move-PtkLegacyEvidence`).
A runtime hardening question remains open below.
**Branch**: `feature/mcp-resilience-r1`
**Found at**: `c618ac3`

## Root cause

Script-evidence artifacts are named by the store. The current format is
`<evidenceId>.<digest>.script` — a 36-character GUID, a dot, and a 64-character
hex digest, giving a 101-character stem. The digest entered the filename in
`460c106` (2026-07-11, "feat: add fail-closed audit foundation").

Builds older than that wrote a **bare GUID** stem, 36 characters, with no digest.
`ScriptEvidenceStore.TryParseEvidenceName` cannot parse those, and an unparseable
artifact is treated as a control violation:

```
throw new ScriptEvidenceControlException(
    "The evidence root contains an invalid artifact.");
```

That surfaces as `ScriptEvidenceStorageException` →
`health.MarkUnavailable("evidence.storage")` → `AuditUnavailableException`.
Audit is mandatory and fails closed, so the entire tool refuses work.

**There was no migration for the format change.** One unrecognised leftover file
is enough to disable the whole audit subsystem, and therefore the whole product.

## Reproduction

This machine's installed binary is dated 2026-07-10 — one day before the format
change — and its `~/.ptk/audit/evidence` holds **12** bare-GUID artifacts.

| Target | Audit root | Result |
|---|---|---|
| guardian | fresh | works |
| guardian | its own, second run | works |
| guardian | real root, `evidence/` removed | works |
| guardian | real root, `spool/` removed | **fails** |
| guardian | real root, untouched | **fails** |
| **plain server** | real root, untouched | **fails** |

Isolated to the evidence directory alone, then to the filename grammar by
instrumenting `ScriptEvidenceStoreProvider.ReconcileExistingAwaitingBeforeWriter`,
which reported `inner=ScriptEvidenceControlException msg=The evidence root
contains an invalid artifact.` File stems on disk measure 36 characters against
the 101 the current format requires.

## Fix

`scripts/dev-install.ps1` gained `Move-PtkLegacyEvidence`, called after the
payload is installed and before registration. It moves artifacts whose stem is a
bare GUID into `~/.ptk/audit/evidence-legacy-<utc-stamp>/`.

- **Moved, never deleted.** These files hold exact submitted scripts. A format
  the store cannot verify is not a reason to destroy the record.
- **Only the legacy shape matches.** Modern artifacts and the store's own state
  suffixes (`.unreferenced.script`, `.anchored.script`, `.local-committed.script`,
  the anchoring form) are left in place.
- Safe by ordering: `Assert-PtkServerNotRunning` has already proven no live
  writer before this point.

Verified against a copy of the real root: 12 artifacts retired, evidence
directory emptied, and **both** the guardian and the plain server then complete a
real `ptk_invoke` returning a working `ptk_output` handle.

## Open: the runtime is still brittle, and that is a design decision

The install path is fixed, but the underlying behaviour is unchanged: an
artifact the store cannot parse disables all auditing and therefore the entire
product. Anyone who upgrades by any other route hits exactly this.

The product fix is to distinguish **"artifact in a format I do not recognise"**
from **"artifact that fails its own integrity check"**. The first is an upgrade
condition and should be quarantined — the store already has an `Unreferenced`
state and a `.unreferenced.script` naming for exactly this kind of set-aside. The
second is tampering and must stay fatal. Today both are fatal.

This is deliberately **not** changed here. Loosening a control-violation path in
the audit subsystem is a security-semantics decision, it should be argued
against the orphan-reconciler and evidence-retention tests that encode the
current rule, and the install-path fix already unblocks the real upgrade. Route
it as its own decision.

Whatever is chosen, the cutover should also verify the server reaches
`audit=available` against the **actual** target root before mutating
registrations. No such check exists, and its absence is what let a
completely inert install look like a success.

## Files changed

`scripts/dev-install.ps1`.

## Guard proof

Not a red-to-green unit proof — the defect lives in an installer path against a
real pre-existing audit root, which no current suite models. The proof is the
reproduction table above, run against copies of the real root: failing before
the migration, passing after it for both binaries, with the artifacts present
and intact in the archive directory afterwards.

The missing regression guard is a test that stands up an audit root containing a
bare-GUID artifact and asserts the server reaches `audit=available`. That belongs
with the runtime decision above, since it is that decision which determines
whether the runtime or the installer is responsible for the outcome.
