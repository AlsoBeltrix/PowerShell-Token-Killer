# r806-1: Containment preflight refusal is reported as an operation that began

**Severity**: MEDIUM — a clean non-start carries `outcome_unknown` and "the operation had already begun" in the trusted structured channel, denying the caller a retry that is actually safe.
**Status**: In progress — fixed and guard-proved; reviewer verification awaits the owner's word
**Branch**: —
**Commit**: (fix committed 2026-08-06; see git history)

## Evidence

`server/PtkMcpServer/Sessions/WorkerSupervisor.cs:489` — `StartedDetailCodes` maps **every** `descendants_unknown` to `OutcomeUnknown`, on the stated theory (remarks, lines 478–488) that close and reset raise that code only AFTER acting on the worker.

`server/PtkMcpServer/Sessions/NamedSessionSupervisor.cs:323` — `ResetAsync` calls `RequireContainmentConfirmedLocked(slot)` as a **preflight**, before the state change at line 327; the same preflight guards close. `NamedSessionSupervisor.cs:1120–1135` — that preflight throws `NamedSessionException("descendants_unknown", …)` at lines 1124 and 1131.

Reachable: a prior operation that leaves `slot.ContainmentEmpty` unconfirmed on a surviving slot (e.g. a start failure with `DescendantsUnknown` containment, lines 607–613), followed by a fresh `ptk_reset` or close, which stops at the preflight having touched nothing.

## Predicted observable failure

After containment is left unconfirmed by a *previous* operation, the next `ptk_reset`/`ptk_session close` that stops at preflight returns disposition `outcome_unknown`, `executed=true`, and text "The operation had already begun; do not assume it did nothing." — all false for the current operation, which never started and is safe to resubmit. A client following the trusted verdict declines a retry it could safely make.

## What

The classifier infers execution stage from the detail code alone, but `descendants_unknown` is emitted at two different stages: post-action (CloseSlotAsync, the case the remarks describe) and preflight refusal (nothing touched). This is the o53 lesson recurring at a third site: PTK stating a false verdict in the channel a client is told to trust. Reviewer's suggested direction: carry the stage on the exception (typed disposition or distinct detail codes for preflight vs post-action), never infer it from a shared string.

## Approach

The reviewer's first suggested direction, taken literally: the stage now travels on the exception. `NamedSessionException` carries `OperationBegan` (default false), set `true` only at the post-action throw site (`StopOldWorkerAsync`, after the worker was stopped with containment unconfirmed). `WorkerSupervisor.Refused` reads the flag; the `StartedDetailCodes` set — the detail-string classifier that could not tell the two stages apart — is deleted, so the class of error (meaning inferred from a shared detail string) is removed at this site rather than patched. Preflight refusals keep their default `false` and now report `not_started`/`safe_to_resubmit=true`/`isError=true`; the post-action refusal keeps reporting `outcome_unknown`. The preflight's refusal *text* changes from "The operation had already begun…" to "Nothing was executed." — a correcting change; the old sentence was the lie.
