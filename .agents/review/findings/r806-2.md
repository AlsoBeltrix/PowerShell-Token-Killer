# r806-2: A failed replacement start reports an executed reset as a non-start

**Severity**: MEDIUM — the reset's destructive half (old worker stopped, warm state lost) is reported as "Nothing was executed" with `safe_to_resubmit=true`; a client observably retains the false belief its warm state survives.
**Status**: Verified — accepted, guard_confirmed true (batch verification, 2026-08-07 04:06 UTC)
**Branch**: —
**Commit**: (fix committed 2026-08-06; see git history)

## Evidence

`server/PtkMcpServer/Sessions/NamedSessionSupervisor.cs:636–664` — `ReplaceSlotAsync` stops the old worker (`StopOldWorkerAsync`), then clears `slot.Worker`, increments the incarnation, and sets `WarmStateLost = true` before `StartSlotAsync` runs.

`server/PtkMcpServer/Sessions/NamedSessionSupervisor.cs:582–619` — any replacement-start failure is wrapped as `NamedSessionException(StartFailureCode(exception), "Session '…' did not start.")`.

`server/PtkMcpServer/Sessions/WorkerSupervisor.cs:497–510` — the classifier treats every detail code except `descendants_unknown` as `NotStarted`: "Nothing was executed.", `executed=false`, safe to resubmit.

## Predicted observable failure

When the replacement worker fails to initialize (spawn failure, initialize timeout) during `ptk_reset`, the tool returns trusted `not_started` / `executed=false` / `safe_to_resubmit=true` even though the old worker was terminated, warm state was discarded, and the session is now Faulted. The text half ("Session '…' did not start.") is true of the replacement but the structured verdict speaks for the whole reset, which did execute destructively.

## What

The disposition is derived from the start-failure detail code, but on the reset path that code describes only the second half of a two-phase operation whose first half already destroyed state. Same defect class as r806-1 and the two o53 follow-ons: stage inferred from a detail string instead of carried as data. Reviewer's suggested direction: propagate a typed disposition from the reset transition — any failure after the old worker is stopped is `failed` or `outcome_unknown`, never `not_started`.

## Approach

Rides the r806-1 mechanism: `StartSlotAsync` takes `operationBegan` and stamps it on both of its completion exceptions (the start-failure wrap and the stale late-start). `ReplaceSlotAsync` passes `true` — by the time it starts the replacement, the old worker is stopped and warm state is gone — and its own stale-reset throw carries `true` for the same reason. The cold-open caller keeps the default `false`: an open that fails to start executed nothing and is safe to retry. Through `Refused` this yields `outcome_unknown`/`executed=true`/`safe_to_resubmit=false` with the start-failure detail code. `outcome_unknown` was chosen over `failed` deliberately: the structured flags that drive client behavior are identical either way, and the reviewer's suggested direction accepted either; the smaller change reuses the proven stage-flag path rather than adding a second channel.

## Files changed
