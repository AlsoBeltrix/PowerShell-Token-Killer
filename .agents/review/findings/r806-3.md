# r806-3: The uninstall containment check accepts sibling paths

**Severity**: HIGH — the only guard on the opt-in destructive uninstall passes a sibling-prefixed home, so the proof can uninstall a home that does not contain the server under proof: exactly the destruction the documented refusal exists to prevent.
**Status**: In progress — fixed and guard-proved; reviewer verification awaits the owner's word
**Branch**: —
**Commit**: (see Files changed / git history: fix committed 2026-08-06)

## Evidence

`server/direct-product-proof.ps1:257` — containment is a raw `$server_.StartsWith($home_, [StringComparison]::OrdinalIgnoreCase)`: no directory-boundary enforcement, and case-insensitive even on POSIX.

`server/direct-product-proof.ps1:282–296` — the uninstall then derives the child's `HOME` from the supplied path's parent and runs `$home_/scripts/install.ps1 -Uninstall`, which targets `$HOME/.ptk` (`scripts/install.ps1`).

Trigger: `-UninstallHome /tmp/proof/.ptk` while `-ServerPath` points under `/tmp/proof/.ptk-old/bin`. `"/tmp/proof/.ptk-old/…".StartsWith("/tmp/proof/.ptk")` is true, so the refusal passes.

The refusal contract is documented in `.agents/repo-guidance.md` (Verification): the uninstall check "refuses unless that root contains the server under proof."

## Predicted observable failure

With a sibling-prefixed layout, the guard passes, the installer uninstalls `/tmp/proof/.ptk` (a different install than the one under proof), and only afterward do the survival checks fail because the server under `.ptk-old` still exists — after the wrong home's payload and registrations are already destroyed. An operator pointing the proof at the wrong of two adjacent test homes gets a destructive uninstall the refusal was written to stop.

## What

Prefix string matching is not path containment. The check must enforce a path-component boundary (e.g. compare with a trailing separator appended, or `[IO.Path]::GetRelativePath` yielding a non-`..`, non-rooted result) and use case sensitivity appropriate to the platform. The reviewer additionally suggests verifying the supplied home matches the installer's derived `$HOME/.ptk` target before starting.

## Approach

Containment is now a path-component test: `[IO.Path]::GetRelativePath($home_, $server_)` must be neither rooted, nor `..`, nor start with `..<separator>` — a sibling-prefixed path yields `../…` and is refused, and the comparison is case-correct per platform (fixes the POSIX over-match too). A second refusal requires the supplied home's leaf name to be literally `.ptk`, because the child process derives `HOME` from the supplied path's parent and the installer always targets `$HOME/.ptk` — any other name would aim the uninstall at a directory other than the one validated.
