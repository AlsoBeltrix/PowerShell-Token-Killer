## Predicted observable failure

On a Windows runner where Defender is unavailable or `MpCmdRun.exe` exits nonzero, the payload is unchanged by definition, the survival comparison passes, the proof exits 0, and the workflow archives a "Defender-proved" Windows artifact whose scan never ran. Same vacuous-gate class as i42-2 (a check that passes with the call deleted).

## What

Payload survival is the right verdict for detections (per the no-EICAR decision), but it only means something if the scan actually completed. The check needs two separable assertions: (1) the scan command ran and completed successfully — missing `MpCmdRun.exe` or a nonzero scanner exit is a failed release check on the RID that claims Defender proof; (2) the payload survived it — the existing comparison.

## Approach

The gate now has the two separable assertions the finding called for. A new `Defender scan completes (#7)` check records the scanner's exit code: 0 (clean verdict) and 2 (threat verdict) both mean the scan completed and the survival check judges the outcome; any other exit fails the check, and an absent `MpCmdRun.exe` now reports that same check failed instead of printing a skip line. The payload-survival comparison is unchanged and still owns the quarantine verdict, so a genuine detection surfaces as a survival failure, not a masked scanner error. The scanner's last output line and exit code travel in the check detail for diagnosis.

**Consequence to note for the pending `0.2.0-rc.3` dispatch:** if GitHub's Windows runners cannot complete an on-demand scan (Defender service disabled), the per-RID gate now fails there *by design* — that is the vacuous pass made visible. The workflow may need to ensure Defender is scannable on the runner, or the owner may move the Defender leg to an operator Windows host; that is an owner call, not something this fix pre-softens.
