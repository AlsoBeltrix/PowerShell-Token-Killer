# r806-5: Invoke's Failed fallback reports machinery failures as completed

**Severity**: MEDIUM — for worker-reported failures whose detail is neither `outcome_unknown` nor a script conclusion, the trusted channel claims `disposition=completed`/`executed=true` for work PTK cannot show ever ran, while the text half of the same response says `status=failed`.
**Status**: In progress — fixed and guard-proved; reviewer verification awaits the owner's word
**Branch**: —
**Commit**: (fix committed 2026-08-06; see git history)

## Evidence

`server/PtkMcpServer/Sessions/WorkerSupervisor.cs:76–79` — the invoke mapping: `WorkerResultStatus.Failed => DetailCode == "outcome_unknown" ? OutcomeUnknown : Completed`.

Producers of `WorkerResultStatus.Failed` on the invoke path whose failure is **not** a script conclusion:

- `server/PtkMcpServer/Worker/WorkerOperationScheduler.cs:272–279` — the executor returned null → detail `invalid_operation_result`.
- `WorkerOperationScheduler.cs:296–303` — an `OperationCanceledException` not owned by the operation's token escaped mid-execution → `operation_failed`.
- `WorkerOperationScheduler.cs:305–312` — any non-fatal exception from `_executor.ExecuteAsync` → `operation_failed`; the exception can be thrown before the pipeline ever starts.
- `WorkerOperationScheduler.cs:372–382` — request/result type mismatch → `invalid_operation_result`.

The intended special case is test-pinned (`server/PtkMcpServer.Tests/ToolOutcomeTests.cs:142`, `(Failed, "execution_failed") → completed`, "a script that ran and threw is a completed call") — but `WorkerSession.MapInvokeResult`'s catch-all arm (`server/PtkMcpServer/Worker/WorkerSession.cs:105`) produces the same `execution_failed` for `InvokeDisposition.Failed` sites that are PTK machinery, not script conclusions: `server/PtkMcpServer/RunspaceHost.cs:3485` and `:3497` (RTK completed but trusted output shaping hung or threw; output discarded; runspace recycled; `WarmStateLost=true`).

Text side: `WorkerSupervisor.cs:338–351` renders `status=failed detail=<code>` for the same result the structured channel labels `completed`.

(`WorkerServer.WriteFailureAsync`'s Failed frames answer only the initialize/shutdown request IDs and reach the session-start/close paths, not this mapping — checked during intake.)

## Predicted observable failure

When a scheduler-level failure fires, the trusted structured channel returns `disposition=completed, executed=true, safe_to_resubmit=false` while the text of the same response says `status=failed detail=operation_failed`. A structured-content client treats the call as a completed execution — for example, reads the empty output of a failed-before-start operation as "the command ran and printed nothing" — and is denied a safe retry for an operation that may never have started. For the RunspaceHost shaping-failure sites, a completed disposition additionally hides that PTK's machinery discarded the output and destroyed warm state (the text and `warm state lost` rider carry it; the disposition contradicts them).

## What

The same root lesson as r806-1/-2 and o53-1/-2, at a fifth site: operation stage and meaning inferred from a shared detail string, with the producer sites unenumerated. The `execution_failed → completed` rule is sound for a script's own terminating error, but the fallback arm sweeps every other Failed detail into `completed`, and `execution_failed` itself is also produced by machinery failures.

Suggested direction: enumerate the Failed detail codes and classify each (`operation_failed`, `invalid_operation_result` → `outcome_unknown` or `failed`), or carry the disposition as data end-to-end from the producer — the worker protocol already distinguishes statuses; machinery failures need their own, rather than sharing `failed` with script conclusions.

## Approach

The Failed arm now enumerates: `outcome_unknown` → `outcome_unknown`; `execution_failed` → `completed` (the pinned "script ran and threw" rule, unchanged); **everything else — including details no current producer emits — falls back to `outcome_unknown`**, flipping the default from overclaiming completion to admitting uncertainty. Residual, accepted: the RunspaceHost shaping-failure sites still share `execution_failed` and therefore still read `completed` — factually defensible there ("the work ran": RTK completed before shaping failed; the machinery failure travels in the text and detail), and separating them needs a worker-protocol change out of proportion to this finding. Recorded here rather than silently dropped.
