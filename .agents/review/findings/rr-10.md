# rr-10: Zero-length audit quota control under concurrent start

**Severity:** HIGH — a shared spool root can become permanently unusable.
**Status:** FIXED on `master`: reworked in `f29784c5` (the control is
created in place again and an empty control means creation in progress,
after CI reopened the accepted `dc85fcf5`) and repaired in the commit
carrying this update after the codex reopen of the rework (below).
Verdict on the repair delta pending. Dispatch provenance in
`.agents/plans/release-0.3.0-rc.6.md`.
**Scope:** `server/PtkMcpServer/Audit/AuditSpoolQuotaLease.cs` and
`server/PtkMcpServer.Tests/AuditSpoolQuotaLeaseTests.cs`.

CI run `40377656597` (ubuntu, head `812bc46c`, 2026-10-26) failed
`FileAuditJournalSinkTests.Concurrent_factories_converge_on_one_host_identity_without_temporary_files`
with `IOException: The audit spool quota control is invalid`, thrown by
`AuditSpoolQuotaLease.VerifyRetainedControl` inside `CreateControlAndAcquire`.
The same test passed 25 of 25 local runs on macOS and on the next CI run, so
the window is small; it is not imaginary.

`EnsureControlFile` created `.ptk-audit-quota.lock` in place with
`FileMode.CreateNew`/`FileShare.None` and wrote the one-byte marker only
afterwards. On Unix, .NET emulates `FileShare` with `flock`, taken after
`open(2)`. A concurrent acquirer can therefore open the still-empty control
and win the exclusive lock between the creator's open and its lock; it then
verifies a zero-length control and fails closed. The creator's own open
fails with a sharing violation, is swallowed by the "a concurrent writer
published it" catch, and nobody ever writes the marker: the zero-byte
control stays, and `EnsureControlFile` returns early on every later start
because the entry exists. Impact: two supervisors initializing one audit root
at the same time can leave that root failing closed until an operator removes
the control by hand.

## Repair and proof

The marker is now complete and durably flushed in an exclusive temporary file
(`.ptk-audit-quota.lock.<guid>.tmp`) and published with
`SecureAuditStorage.PublishAtomically`, the no-replace primitive the host
identity already uses (`MoveFileEx` without replace on Windows, hard link
plus unlink on POSIX). A creator that loses the publish race discards its
copy and acquires the winner's control, which the existing exclusive
acquisition still validates byte for byte. Any other failure removes the
temporary file and propagates.

Guards: `Writer_creation_never_exposes_a_partial_control` hooks the instant
before publication and asserts the control name does not exist while the
pending file already carries the full marker, then that no temporary file
survives; `Concurrent_writer_creations_converge_on_one_control_without_temporary_files`
holds eight creators at that instant with a barrier and releases them to
publish at once. Red evidence is the CI failure itself: the old window lies
inside .NET's open-to-lock sequence and cannot be forced from a test, so the
guards encode the invariant the fix establishes rather than replaying the
race. Focused lease and journal-sink tests: 65/65 on this host. Full server
suite: 1,398/1,398 (the two new guards included) on a clean rerun; a
first run under host load (eleven minutes instead of under three) failed
two unrelated timing tests once, `UnixWorkerContainmentRegistryTests.
A_transient_identity_failure_does_not_release_a_live_escape` and
`InvokeToolTests.Timeout_response_does_not_wait_for_the_replacement_runspace`,
neither with a recorded flake history. `git diff --check` clean.

## Reviewer reopen (codex, 2026-10-27) and repair

Codex (gpt-5.6-sol/high, pins `eb25ccb0..0d498d7d`) reopened: the POSIX
publish is `link(temp, control)` then `unlink(temp)`, so the inode carries
two links in between; an acquirer that opens the control in that interval
reaches `VerifyRetainedControl`, whose identity check requires exactly one
link on Unix and throws an `IOException` that `TryAcquireExistingCore` does
not treat as contention. The losing creator, or any `AcquireExisting`
caller, fails instead of converging. Confirmed by reading
`SecureAuditStorage.PublishAtomically` and
`UnixNative.GetProtectedFileIdentity`. The interval is transient (the
control is valid once the temporary name is gone), so the impact is a
startup failure for the second process, not a poisoned root. The reviewer
also confirmed that the incomplete-content exposure is closed, the Windows
move is sound, and existing controls are unaffected.

Repair: the creator keeps its exclusive handle on the temporary file open
across `PublishAtomically`. On Unix .NET backs `FileShare.None` with
`flock(LOCK_EX)` on the inode, so an exclusive open of the published name
during the two-link interval fails with `EWOULDBLOCK`, which
`IsSharingViolation` already classifies as contention: `TryAcquireExisting`
returns false and `AcquireExisting` retries until the creator releases the
handle after the unlink. On Windows the handle is released before the
no-replace move (it carries no delete sharing); the move itself is atomic.
`PublishAtomically` gained the seam `publishedNameLinkedForTests`, invoked
inside the interval (after the link, before the unlink).

Guard `Acquirers_during_control_publication_wait_instead_of_failing`: from
inside that seam it probes `TryAcquireExisting` (contention on POSIX, the
complete control on Windows) and starts a blocking `AcquireExisting` that
must succeed once the creator finishes. Red on the previous fix (handle
released before the publish) with the predicted
`IOException: The retained audit segment type, owner, mode, or link count
is invalid` from `ValidateMacRetainedFile` via `TryAcquireExisting`; green
with the repair. `Writer_creation_never_exposes_a_partial_control` now
inspects the pending file by name only, since its handle is exclusive.
Focused lease, journal-sink, storage and factory suites 81/81; full server
suite 1,399/1,399 in 2 m 37 s; `git diff --check` clean. Not replayed on
Linux or Windows locally; CI covers both.

## Verdict (codex, 2026-10-27)

Accepted, pins `fc240a2e..dc85fcf5` (the echoed head SHA matches). The
reviewer confirmed that on Linux and macOS acquirers meet the retryable
sharing violation before link-count validation and that the lock stays
valid after the unlink because it belongs to the open inode; found no
conflict between the held lock and the publish's path checks or directory
fsync; losing creators dispose their handles before cleanup; every success
and failure path removes the temporary name; a waiting acquirer cannot
deadlock the publisher; Windows closes the handle before the move; existing
controls keep the unchanged early return. Linux and Windows were not
replayed locally; source inspection showed no platform-specific gap.

## Second reopen (CI evidence, 2026-10-27) and rework

CI run `40386199045` at `fc240a2e` (the head carrying `0d498d7d`) failed
`FileAuditJournalSinkTests.Concurrent_factories_converge_on_one_host_identity_without_temporary_files`
on both ubuntu and macos with `IOException: The audit spool contains an
unknown entry` from `RecoverCrashTemporaryArtifactsAndValidateSpool`: the
temporary name `.ptk-audit-quota.lock.<guid>.tmp` of a concurrent creator
was still in the spool root while the lease holder validated it. Every
spool inventory (the journal sink's recovery and segment enumeration, the
closed-chain reader, the evidence scanner, retirement, anchored prefix
retention and anchored writer preparation) accepts the control name and
parseable segment names only and fails closed on anything else, so a
temporary name in the spool root can never be safe, whatever the publish
primitive does. Neither codex verdict saw this, and the repair in
`dc85fcf5` (holding the handle across the publish) does not touch it.

Rework: the control is created in place again, as before `0d498d7d`, with
one rule added for the race the original finding described. An empty
control means "creation in progress": `CreateControlAndAcquire`, the only
path that may create the control, is also the only path that may complete
one, and does so under its own exclusive lock when it finds the control
empty; `AcquireExisting` retries while the control stays empty (bounded by
the same thirty seconds) and `TryAcquireExisting` reports it as owned. So
the acquirer that wins the lock between a creator's `open(2)` and its
`flock` no longer fails closed on a zero-length control, and the creator,
whose own open failed as a sharing violation, completes the control in its
acquisition. A creator that crashes before its one-byte write leaves an
empty control that the next creator completes; until then non-creating
acquirers wait and then fail, rather than failing at once, which is the one
semantic change (an empty control is no longer a malformed one in the test
data). `PublishAtomically` is back to its pre-rr-10 shape; no seam remains.

Guards: `Concurrent_writer_creations_converge_on_one_control_and_nothing_else`
(eight creators; the root ends with exactly the control) and
`Empty_control_counts_as_creation_in_progress_until_a_writer_completes_it`
(a zero-length control: the probe reports an owner, a blocking acquirer
waits, the next creator completes it, the waiter then acquires). The
seam-based guards are removed with the seams. Red evidence: the previous
code's own theory asserted that an empty control throws from
`TryAcquireExisting`, and the CI failure above is the unknown-entry case.
Focused suites 79/79; full server suite 1,397/1,397 in 2 m 38 s (three
guards removed, two added, one theory case removed); `git diff --check`
clean. Not replayed on Linux or Windows locally; CI covers both.

## Reopen of the rework (codex, 2026-10-27) and repair

Codex (pins `1302b4be..f29784c5`) confirmed that the rework closes both
races on Unix and that a permanently empty control only delays
non-creating acquisition by the bounded thirty seconds, and reopened on
two points. First, on Windows `CreateExclusiveFile` made the name visible
with the default DACL until `ProtectFile` applied the owner-only
descriptor, so a concurrent acquirer validating the path in that instant
failed closed instead of retrying, and a creator killed in it stranded an
empty, misprotected control that later creators skip (the name exists)
and no acquisition accepts. Second, the completion wrote the marker before
the retained identity and link-count proof, so an empty control carrying
a second hard link was written through every name before rejection.

Repair: on Windows, `CreateExclusiveFile` now creates the file through
`FileSystemAclExtensions.Create` with the owner-only descriptor
(`CurrentUserOwnerOnlyFileSecurity`: current user as owner, protected
DACL, one non-inheritable full-control allow, the shape
`VerifyWindowsOwnerOnlyAcl` accepts) in the create call itself, so the
name is never visible unprotected; `ProtectFile` still re-applies the
exact shape afterwards. Preallocated files keep the plain create, since
the descriptor-bearing create cannot preallocate (segments are created
under the lease and are not validated by a concurrent acquirer). The
completion of an empty control now proves the path and the retained
identity (single link, exact path) before writing, then runs the full
verification as before.

Guard `Empty_control_with_a_second_name_is_rejected_before_it_is_written`:
an empty control with a hard-linked alias makes `CreateControlAndAcquire`
throw and leaves both names empty; red on `f29784c5` (the control had
been written, so `Assert.Empty` on its bytes failed), green with the
repair. The Windows descriptor-at-create change has no seam to observe
the instant of creation; its proof is the create call carrying the
descriptor and the Windows CI leg on this head. Focused suites 80/80;
full server suite 1,398/1,398 in 2 m 44 s; `git diff --check` clean; the
two baseline xUnit2002 analyzer warnings only.
