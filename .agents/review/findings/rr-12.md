# rr-12: An rtk inside the payload directory is accepted, then deleted by the upgrade

**Severity:** MEDIUM — affected users cannot upgrade with `-FromRelease`;
every attempt rolls back.
**Status:** FIXED on `master` in three commits, `23e11dbc`, `b2db2dab` and
the commit carrying this update (after the two codex reopens below);
verdict on the third delta pending. Provenance in
`.agents/plans/release-0.3.0-rc.6.md`.
**Source:** codex Change review over `74aaeaf..eb25ccb0` (2026-10-27),
first candidate; admitted after reading `Install-PtkRtk`, `Find-PtkRtk`,
`$payloadEntries`, `RtkDependency.ResolveExecutablePath` and the rc.5
installer.
**Scope:** `scripts/install.ps1` (`Find-PtkRtk`, `Install-PtkRtk`, the
pre-staging checks) and `tests/PwshTokenCompressor.Tests.ps1`.

Installers up to rc.5 (2026-10-24) downloaded rtk into `~/.ptk/bin`, which
the server never searches; the ways around that were to put the directory
on `PATH` or to point `PTK_RTK_PATH` at the copy. `bin` is one of the
payload entries the installer replaces wholesale on upgrade. The rc.6
installer's `Find-PtkRtk` took the first `rtk` that `Get-Command` found, so
with `~/.ptk/bin` on `PATH` it accepted the legacy copy ("rtk found on
PATH"), activation deleted it with the old payload, the installed smoke test
started a server that exits 78 without rtk, and the transaction rolled back.
With `PTK_RTK_PATH` pointing into the payload the result is the same by the
other route: the server takes `PTK_RTK_PATH` over `PATH` with no fallback,
the installer never looked at it, and the installed server would fail on a
path the upgrade had just removed.

## Repair and proof

`Find-PtkRtk` now walks every `rtk` on `PATH` in order (`Get-Command -All`,
as the server searches) and skips any inside `~/.ptk/bin`
(`Test-PtkPayloadRtk`); `Install-PtkRtk` names a skipped copy before
installing into `~/.local/bin`. A `PTK_RTK_PATH` inside the payload is
refused before any question (`Assert-PtkRtkPathOutsidePayload`, placed with
the other no-answer checks ahead of `Assert-PtkRtkConsent`), telling the
user to unset it or point it outside that directory. The legacy copy is
removed with the old payload as before, and `Remove-PtkInstalledRtk` still
understands the old path-only marker.

Guard `never relies on an rtk inside the payload it replaces`: the real
`Find-PtkRtk`, `Test-PtkPayloadRtk` and `Assert-PtkRtkPathOutsidePayload`
bodies against fake executables, with `PATH` set to the payload directory
alone (expect none), the payload plus another directory (expect the other),
and `PTK_RTK_PATH` inside the payload (expect the refusal) and outside it
(expect the lookup to proceed). Red evidence: the `Find-PtkRtk` body from
`fc240a2e`, run in the same harness with only the payload rtk on `PATH`,
returns that payload path. The order pin `refuses a doomed build before
asking anything...` now includes the new check, and `installs rtk where
PATH can reach it...` loads `Test-PtkPayloadRtk` beside the bodies it
exercises. Filtered rtk tests 15/15; full Pester suite 131 passed, 0
failed, 3 platform-skipped (with the hook-publish override from
`.agents/machines.md`); `git diff --check` clean. Not exercised as a live upgrade in a
throwaway home; the transaction's wholesale `bin` replacement is existing,
tested behavior.

## Reviewer reopen (codex, 2026-10-27) and repair

Codex (pins `dc85fcf5..23e11dbc`) accepted the direct `PATH` repair and
the legacy-marker handling, and reopened on two points. First,
`PTK_RTK_PATH` was still not resolved as the server resolves it: the
installer only rejected a configured path inside the payload and then
searched `PATH`, while the server uses only the configured path, with no
fallback. So a valid configured path with no rtk on `PATH` counted as
missing (a redundant install, or a refusal if declined), and an unusable
configured path beside a working `PATH` copy was accepted although the
smoke test's server would then fail on it. Second, containment was
lexical: a symbolic link outside the payload that points into it was
accepted, which brings back the delete-then-fail sequence (a plausible
rc.5 workaround is `ln -s ~/.ptk/bin/rtk ~/.local/bin/rtk`). Codex also
noted that the case-insensitive comparison on macOS can misclassify a
differently-cased path on a case-sensitive volume; that is kept
deliberately: a false match only costs a redundant install into the rtk
directory, while a miss reproduces the rollback, and the comparison stays
ordinal on Linux.

Repair: `Find-PtkRtk` now mirrors `RtkDependency.ResolveExecutablePath`:
when `PTK_RTK_PATH` is set it is the only candidate (outside the payload,
existing, answering the probe), otherwise the first answering rtk on
`PATH` outside the payload. `Assert-PtkRtkPathUsable` (replacing
`Assert-PtkRtkPathOutsidePayload` ahead of the consent question) refuses a
configured path that is inside the payload, missing, or mute, saying why
and that installing elsewhere would not help. `Test-PtkPayloadRtk` compares
real paths on both sides through `Resolve-PtkRealPath`, which follows
every file and directory link component.

Guard extended: configured-only resolution with nothing on `PATH`; a
configured path inside the payload, missing, or mute beside a working
`PATH` copy (each refused with its reason); and, off Windows, a symbolic
link into the payload both on `PATH` (skipped) and as the configured path
(refused). Red evidence: the `Find-PtkRtk` body from `23e11dbc`, in the
same harness, returns nothing for a valid configured path with an empty
`PATH` and returns the link for a symlink into the payload. Filtered rtk
tests 16/16; full Pester suite 132 passed, 0 failed, 3
platform-skipped; `git diff --check` clean.

## Second reopen (codex, 2026-10-27) and repair

Codex (pins `e44b3df6..b2db2dab`) accepted the configured-only precedence,
the missing and mute refusals, ordinary links, missing tail components,
hidden components and the Windows drive-root walk, and reopened on three
points: (1) with the configured path now refusable, the case-insensitive
comparison on a case-sensitive macOS volume turns a false containment
match into a wrong refusal of a path the server accepts, not the redundant
install recorded above; (2) a whitespace-only `PTK_RTK_PATH` counted as
configured, while the server's `IsNullOrWhiteSpace` check falls back to
`PATH`; (3) `Resolve-PtkRealPath` returned a partially resolved path after
its sixteen passes without verifying stability.

Repair: case sensitivity is asked of the filesystem instead of assumed per
platform (`Test-PtkCaseInsensitiveDirectory` probes the payload directory's
name with its letters' case flipped; a name without letters falls back to
the platform default); a whitespace-only `PTK_RTK_PATH` is unset for the
installer as for the server; the resolver throws when a chain is still
changing after its pass limit, or loops, and a candidate that cannot be
resolved is skipped on `PATH` and refused as the configured path, with the
reason.

Guard extended: a whitespace-only configured value beside a working `PATH`
copy (found); the probe's answer for the test volume (`-not $IsLinux`); a
differently-cased spelling of the payload directory on `PATH` (contained
where it resolves); off Windows, a directory link whose target passes
through another link (two passes) and a self-looping link (skipped on
`PATH`, refused when configured). Red evidence: the `b2db2dab` bodies, in
the same harness, refuse a whitespace-only `PTK_RTK_PATH` beside a working
`PATH` copy ("does not exist"). Filtered rtk tests 16/16; full Pester
suite 132 passed, 0 failed, 3 platform-skipped; `git diff --check` clean.
