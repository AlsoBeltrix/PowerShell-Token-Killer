# rr-13: The installer overwrites, adopts and later uninstalls a user's rtk at the install target

**Severity:** LOW — narrow trigger; the user's own rtk binary is replaced
without asking and removed by a later uninstall.
**Status:** FIXED on `master` in two commits, `3cfc06a1` and the commit
carrying this update (after the codex reopen below); verdict on the
repair delta pending. Provenance in `.agents/plans/release-0.3.0-rc.6.md`.
**Source:** codex Change review over `74aaeaf..eb25ccb0` (2026-10-27),
third candidate; admitted after reading `Install-PtkRtkRelease`,
`Install-PtkRtk` and `Remove-PtkInstalledRtk`.
**Scope:** `scripts/install.ps1` (`Assert-PtkRtkConsent`, new
`Assert-PtkRtkTargetFree`) and `tests/PwshTokenCompressor.Tests.ps1`.

When no rtk on `PATH` answers, the installer fetches one into
`$RTK_INSTALL_DIR` (default `~/.local/bin`, rtk's own default): on Windows
`Install-PtkRtkRelease` copies `rtk.exe` there with `-Force`, and on Linux
and macOS rtk's `install.sh` overwrites `rtk` there itself. The marker then
records that path and hash as the copy this installer placed, so
`Remove-PtkInstalledRtk` deletes it on uninstall. A user who put their own
rtk in that directory without adding it to `PATH` (or whose copy fails the
`rtk rewrite` probe) therefore had it replaced silently and later removed.

## Repair and proof

`Assert-PtkRtkTargetFree` runs inside `Assert-PtkRtkConsent` after the
lookup fails and before the question is asked (a check that needs no
answer): if the target exists and the marker does not record exactly that
path with its current hash, the installer stops and tells the user to add
the directory to `PATH` or remove the file, then re-run. The installer's
own earlier copy (same path, same hash) may still be replaced, so a re-run
after a `PATH` fix behaves as before. Nothing is fetched before the check.

Guard `refuses to overwrite an rtk it did not place at the install target`:
the real `Assert-PtkRtkConsent` and `Assert-PtkRtkTargetFree` bodies with
no target (proceeds), the installer's own copy (proceeds), a foreign copy
without a marker (refused) and a copy whose hash differs from the marker
(refused). Red evidence: the `Assert-PtkRtkConsent` body from `23e11dbc`,
run in the same harness with a foreign rtk at the target, proceeds. The
decline test stubs the new check. Filtered rtk tests 16/16; full Pester
suite 132 passed, 0 failed, 3 platform-skipped (hook-publish
override from `.agents/machines.md`); `git diff --check` clean.

## Reviewer reopen (codex, 2026-10-27) and repair

Codex (pins `22862834..3cfc06a1`) confirmed the platform target names,
that hashless pre-2026-10-24 markers are not trusted, that a working
target on `PATH` bypasses the refusal, and that a legitimately upgraded
copy is used when it answers and otherwise preserved, and reopened on
two points. First, ownership was a case-insensitive string compare of
unresolved paths (`$ours -eq $target`): on a case-sensitive filesystem
case-different paths are different files, and a relative
`RTK_INSTALL_DIR` resolves differently between runs under the same
marker text, so a user's copy with the same bytes as ours could be
accepted, overwritten, adopted and later removed. Second, the check ran
before consent but the write happened later, after the prompt, the SDK
installation and the download, with no revalidation, so a file created
or replaced meanwhile could still be overwritten.

Repair: the install directory is made absolute once at startup
(`[IO.Path]::GetFullPath`), so the marker names one file whatever a later
run's working directory is. Ownership (`Test-PtkInstalledRtk`) is the
same file by identity: the marker's directory and the target's directory
must share the identity rr-12 established (`stat` device and inode on
Unix, volume serial and 128-bit file id on Windows), the names must be
equal ordinally, and the file must still carry the recorded hash. The
write boundary is now the only write: the fetch lands in a private
staging directory beside the target (`Install-PtkRtkRelease` copies the
extracted `rtk.exe` there; `Install-PtkRtkWithScript` points rtk's
`install.sh` at it through `RTK_INSTALL_DIR` for the child only), the
installer's own earlier copy at the target is removed first (proved by
marker and hash), and the binary is placed with `[IO.File]::Move(…,
overwrite: false)`, which on Unix links the new name and only then
unlinks the staged one and on Windows moves without replacement; a file
that appeared at the target since the check makes the move fail, the
installer refuses ("rtk appeared at … while this installer was fetching
one"), nothing is recorded, and the staging directory is removed.

Guard extended: a marker naming another directory's file with the same
bytes is refused (ownership is identity and name, not string or hash
alone); the installer's own copy is replaced in place; a clean target is
placed and recorded with no staging left behind; a foreign rtk that
appears after the consent check is never overwritten, nothing is
recorded, and no staging remains; and the absolute install directory is
pinned. The `installs rtk where PATH can reach it` and rr-12 install
harnesses now stage their fakes as the real fetchers do. Red evidence:
the `3cfc06a1` bodies, with a fake fetch that plants a foreign file at
the target after consent, report "installed" over it. Filtered tests
17/17; full Pester suite 133 passed, 0 failed, 3 platform-skipped;
`git diff --check` clean. rtk's `install.sh` was not run live here (the
rr-9 route proof still needs the owner's go); the staging redirection is
the documented `RTK_INSTALL_DIR` contract the earlier verification of
the script recorded.
