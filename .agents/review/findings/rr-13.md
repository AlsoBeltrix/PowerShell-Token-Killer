# rr-13: The installer overwrites, adopts and later uninstalls a user's rtk at the install target

**Severity:** LOW — narrow trigger; the user's own rtk binary is replaced
without asking and removed by a later uninstall.
**Status:** FIXED on `master` (the commit carrying this record); codex
verdict pending (per-finding dispatch after rr-12 closes). Provenance in
`.agents/plans/release-0.3.0-rc.6.md`.
**Source:** codex Change review over `74aaeaf..eb25ccb0` (2026-10-27),
third candidate; admitted after reading `Install-PtkRtkRelease`,
`Install-PtkRtk` and `Remove-PtkInstalledRtk`.
**Scope:** `scripts/install.ps1` (`Assert-PtkRtkConsent`, new
`Assert-PtkRtkTargetFree`) and `tests/PwshTokenCompressor.Tests.ps1`.

When no rtk on `PATH` answers, the installer fetches one into
`$RTK_INSTALL_DIR` (default `~/.local/bin`, rtk's own default): on Windows
`Install-PtkRtkRelease` copies `rtk.exe` there with `-Force`, and on Linux
and macOS rtk's `install.sh` overwrites `rtk` there itself. The marker then
records that path and hash as the copy this installer placed, so
`Remove-PtkInstalledRtk` deletes it on uninstall. A user who put their own
rtk in that directory without adding it to `PATH` (or whose copy fails the
`rtk rewrite` probe) therefore had it replaced silently and later removed.

## Repair and proof

`Assert-PtkRtkTargetFree` runs inside `Assert-PtkRtkConsent` after the
lookup fails and before the question is asked (a check that needs no
answer): if the target exists and the marker does not record exactly that
path with its current hash, the installer stops and tells the user to add
the directory to `PATH` or remove the file, then re-run. The installer's
own earlier copy (same path, same hash) may still be replaced, so a re-run
after a `PATH` fix behaves as before. Nothing is fetched before the check.

Guard `refuses to overwrite an rtk it did not place at the install target`:
the real `Assert-PtkRtkConsent` and `Assert-PtkRtkTargetFree` bodies with
no target (proceeds), the installer's own copy (proceeds), a foreign copy
without a marker (refused) and a copy whose hash differs from the marker
(refused). Red evidence: the `Assert-PtkRtkConsent` body from `23e11dbc`,
run in the same harness with a foreign rtk at the target, proceeds. The
decline test stubs the new check. Filtered rtk tests 16/16; full Pester
suite 132 passed, 0 failed, 3 platform-skipped (hook-publish
override from `.agents/machines.md`); `git diff --check` clean.
